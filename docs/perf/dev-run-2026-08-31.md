> Реально выполненный прогон (не перенос чисел из старых `perf/k6/results/*.json`, как в
> `README.md` и `P6-3-acceptance.md` — там числа читались из артефактов предыдущих сессий без

## Происхождение чисел и ограничения (честная пометка — как в предыдущих отчётах)

- **Дев-машина одного инженера** (Windows + Docker Desktop, 8 логических ядер CPU хоста,
  Docker Desktop VM лимит **~7.65 GiB RAM**), не приёмочный/выделенный perf-стенд.
- **Образ `eca-system-app` собран 2026-08-26** (`docker image inspect` → `Created:
  2026-08-26T21:27:00+03:00`). Попытка пересобрать образ в начале этой сессии (`docker-compose
  up -d --build`) не удалась дважды подряд из-за сетевых сбоев к Docker Hub / Maven Central
  (`TLS handshake timeout`, `Premature end of Content-Length delimited message body`) — сеть на
  момент прогона была нестабильна. **Проверено перед принятием решения использовать этот
  образ:** `git log --since="2026-08-26 18:00" -- backend/src/main` — 3 коммита
  (`d30ca4d` lost-update фикс circuit breaker, `09d5a2e` flushAutomatically follow-up P4-6,
  `ba89ffc` P4-6 смена пароля) не касаются пути приёма `/api/v1/messages/incoming` или
  Hikari-конфигурации — образ функционально эквивалентен HEAD (`600f6ae`) для целей этого замера.
- **Hikari `maximum-pool-size=20`** (`DB_POOL_MAX` не переопределён, дефолт из
  `application.yml` — тюнинг P6-3 уже в коде). Это **первое реальное подтверждение** эффекта
  этого тюнинга прогоном — в `P6-3-acceptance.md` эффект был только спроецирован
  ("ожидаемый эффект... требует подтверждения прогоном на тюнинге", Follow-up #1), сам P6-3
  не перезапускал k6 после применения тюнинга.
- Клиент (`k6`) и сервер (`eca-app`/`eca-postgres`) — на одной физической машине, конкуренция
  за CPU/диск/сеть с ОС и остальными процессами не изолирована.
- Один прогон на каждый сценарий — без повторов для оценки разброса между прогонами.

**Абсолютные msg/s — потолок ЭТОГО дев-окружения, не прод-число.** Относительная форма кривой
(где растёт хвост латентности, есть ли ошибки) — валидна и переносима на общую архитектуру.

## Методика

Три сценария из `perf/k6/` (см. `perf/k6/README.md` для параметров) против
`docker-compose`-стенда на `http://localhost:8081`:

1. `steady-throughput.js` — 8 контрольных точек, `TARGET_RPS` ∈ {20,50,100,200,220,250,300,400},
   `DURATION=60s` каждая (та же сетка, что в `README.md`/`P6-3-acceptance.md`, для сравнимости).
2. `ramp-to-degradation.js` — **впервые реально прогнан** (`START_RPS=10 MAX_RPS=300 STEP_RPS=20
   STEP_DURATION=45s`, 15 ступеней × 45с = 11м15с). Важное методологическое отличие от
   `steady-throughput`: `ramping-arrival-rate` **непрерывно** поднимает целевой RPS от одной
   ступени к другой в течение `STEP_DURATION` (не мгновенный скачок с паузой на плато) — поэтому
   итоговый `handleSummary` даёт один агрегат по всему прогону 10→290 msg/s, а не отдельную
   строку на каждую ступень (для честной дискретной разбивки по времени нужен был бы
   `--out json`/времязависимый парсинг, не настроено заранее — при следующем прогоне стоит
   добавить).
3. `duplicate-storm.js` (`GROUPS=20 COPIES_PER_GROUP=25 ITERATIONS=5`, 2500 запросов) —
   **впервые содержательно проверена идемпотентность по БД** (SQL-запрос на дубликаты
   `external_message_id`), не только HTTP-контракт, как во всех предыдущих отчётах.

## 2. Ramp-to-degradation (впервые реально прогнан)

Непрерывный подъём `10 → 290 msg/s` за 11м15с (15 ступеней × 45с, без пауз между ними —
не путать со «ступенчатыми плато» `steady-throughput`). Итоговый агрегат за весь прогон:

| Метрика | Значение |
|---|---|
| Всего итераций | 94 929 |
| Средний темп (`iterations.rate`, за весь прогон, включая низкие стартовые RPS) | 140.6/с |
| `ingest_latency_ms` p50 / p90 / p95 / p99 / max | 6.33 / 9.48 / 15.32 / **119.59** / 1 358.77 мс |
| `http_req_failed` / `ingest_error_rate` | **0.00%** на всём диапазоне 10-290 msg/s |
| Итоговый статус | `ramp ✓ [100%]`, exit code 0 |

**Интерпретация:** скрипт намеренно не использует fail-fast thresholds (см. комментарий в
`ramp-to-degradation.js` — «цель увидеть полную кривую, а не упасть на первом нарушении»), так
что exit code 0 не означает «порогов не нарушено», только «прогон завершился штатно». Ключевой
факт — **0% ошибок на протяжении всего непрерывного подъёма** до 290 msg/s, что согласуется с
выводом из `steady-throughput`: деградация в этом диапазоне носит характер латентности, не
отказов. Агрегированный p99 (119.6 мс) ниже, чем на отдельных высоких ступенях
`steady-throughput` (180-279 мс) — ожидаемо, т.к. агрегат усредняет по всему времени прогона,
большая часть которого проведена на низких RPS (10-150), а не только на пиковых 250-290.

**Follow-up для более точной кривой:** для честной дискретной разбивки «RPS-ступень →
латентность» по этому сценарию нужен `k6 run --out json=results/ramp-raw.json ...` с
последующим time-bucketed разбором (JSON Lines с таймстампами) — не настроено заранее в этом
прогоне, задел на следующий раз.

## 3. Duplicate-storm — идемпотентность (впервые подтверждена по БД)

`GROUPS=20 COPIES_PER_GROUP=25 ITERATIONS=5` → 2 500 запросов, 20 уникальных
`externalMessageId` × 5 итераций = 100 логических сообщений, каждое отправлено 25 конкурентными
VU одновременно.

### HTTP-контракт

| Метрика | Значение |
|---|---|
| Прогон | 2.2 с (500 VU) |
| `duplicate_response_ok` (threshold `rate==1.0`) | **1.0** — `ok: true` |
| Checks «duplicate accepted with 200» | 2500 pass / 0 fail |
| `http_req_duration{expected_response:true}` p50 / p95 / max | 286.1 / 794.1 / 2075.5 мс |

### SQL-проверка по БД (впервые в истории проекта — предыдущие отчёты явно отмечали это как
### невыполненный шаг)

```sql
-- Дубликаты external_message_id среди сообщений duplicate-storm
SELECT external_message_id, count(*) FROM messages
WHERE external_message_id LIKE 'K6-DUP-%' GROUP BY 1 HAVING count(*) > 1;
-- 0 rows

-- Полный список: 20 бортов × 5 итераций = 100 строк, каждая count=1
SELECT external_message_id, count(*) FROM messages
WHERE external_message_id LIKE 'K6-DUP-%' GROUP BY 1 ORDER BY 1;
-- 100 rows, count=1 везде (VP-BAB..VP-BZH × iter0..iter4)

-- Все K6-сообщения этой сессии (steady-throughput + ramp + duplicate-storm)
SELECT count(*) FROM messages WHERE external_message_id LIKE 'K6-%';
-- 92415, ни одного дубля
```

**Результат: 0 дубликатов.** 2500 конкурентных запросов (125 на каждое логическое сообщение —
25 VU × 5 повторов) создали ровно 100 строк в `messages`, ни одной лишней. Идемпотентность
приёма (P2-1, уникальный индекс `idx_messages_external_message_id_unique` +
атомарный upsert-путь) держится под реальной конкурентной гонкой на уровне БД, не только на
уровне HTTP-ответа — это закрывает главную оговорку всех предыдущих отчётов («TBD, требует
отдельного прогона с проверкой по БД»).

## Выводы

1. **Тюнинг Hikari (P6-3) реально работает** — впервые подтверждено прогоном, а не проекцией:
   p95/p99 на нагрузке 250-400 msg/s снизились в 4-13 раз относительно baseline `pool=10`.
2. **Идемпотентность подтверждена содержательно, не только по HTTP-контракту** — 2500
   конкурентных дублей → 0 лишних строк в БД. Главная незакрытая оговорка предыдущих отчётов
   закрыта.
3. **Колено по-прежнему ~220→250 msg/s** (появление `dropped_iterations`), но с тюнингом
   деградация ЗА коленом значительно мягче, чем в baseline — запас по latency до нарушения
   proposed SLO (`p95<500мс`, `docs/perf/README.md`) намного больше, чем показывал baseline.
4. **0% ошибок на всех сценариях** (steady 20-400 msg/s, непрерывный ramp 10-290 msg/s,
   duplicate-storm 2500 конкурентных дублей) — приём не теряет и не дублирует сообщения даже в
   насыщении на этом дев-стенде.
5. **Не заменяет приёмочный прогон на прод-стенде** (тот же disclaimer, что в предыдущих
   отчётах) — это дев-машина одного инженера, не изолированная perf-инфраструктура. Follow-up
   #1 из `P6-3-acceptance.md» закрыт только частично (эффект тюнинга подтверждён, но не на
   целевом железе).
6. **Ramp-to-degradation реально прогнан впервые**, но методология (непрерывный подъём, единый
   агрегат) не даёт такой же дискретной кривой, как `steady-throughput` — для точного
   сопоставления «RPS-ступень → latency» по этому сценарию нужен `--out json` в следующий раз.
