## ВАЖНО: статус и происхождение чисел

Числа в разделе «Результаты» — это **реальные значения**, перенесённые без изменений из
JSON-сводок k6 (`perf/k6/results/*.json`, `handleSummary`), полученных предыдущей рабочей
сессией прогоном `docker run grafana/k6 ...` против локального `docker-compose up --build`
(Windows + Docker Desktop, без k6 binary в PATH — см. `perf/k6/README.md`).

Эта сессия **не располагала** ни установленным k6, ни поднятым стендом (`docker-compose`
не был запущен на момент написания отчёта) — поэтому результаты **не были и не могли быть
повторно провалидированы** в рамках этой задачи. Все 9 файлов в `perf/k6/results/` прочитаны
напрямую и содержат структурно валидные k6-summary (`metrics`, `root_group.checks`,
`state.testRunDurationMs` и т.д.) — нет признаков того, что они сфабрикованы вручную
(согласованные `http_reqs.rate` ≈ заданный `TARGET_RPS`, монотонный рост `vus_max` и
`dropped_iterations` со ступенью нагрузки, правдоподобный разброс латентности). Тем не менее
эти данные:

- получены на **дев-машине одного инженера** (Windows + Docker Desktop), не на приёмочном
  стенде и не в изолированном перф-окружении;
- не сопровождаются информацией о ресурсах хоста (CPU/RAM, выделенных Docker Desktop) и о
  параллельной нагрузке на машине во время прогона;
- однократны — нет повторов для оценки разброса между прогонами.

**Поэтому весь раздел «Результаты» — индикативный прогон, требующий подтверждения на
приёмочном (или хотя бы выделенном CI-perf) стенде.** Использовать эти числа как финальные
приёмочные показатели промышленной системы нельзя. Это зафиксировано явно по требованию
задачи P2-7 (запрет на фабрикацию/выдачу индикативных чисел за финальные).

## 1. Цель и предлагаемые SLO (proposed)

Точных цифр от заказчика (ФГУП «ЗащитаИнфоТранс») на момент задачи нет — приводимые ниже
показатели — **proposed SLO**, обоснованные ожидаемым объёмом ACARS-трафика для замены SITA
AIRCOM Sequencer уровня крупного авиаперевозчика/группы аэропортов, и должны быть
пересмотрены/подтверждены архитектором и заказчиком до приёмочного нагрузочного прогона.

| Показатель | Предлагаемое целевое значение | Обоснование |
|---|---|---|
| Целевой устойчивый throughput входящих ACARS-сообщений | **50–100 msg/s** устойчиво | Крупный российский перевозчик — порядка 200–400 одновременных рейсов в воздухе/на земле в пике; типичная плотность ACARS-сообщений (downlink OOOI/position/status + uplink/ground) — единицы сообщений в минуту на рейс ⇒ десятки msg/s суммарно, с запасом на пиковые всплески (массовые position report, погодные/диспетчерские рассылки) — отсюда верхняя планка 100 msg/s |
| Количество одновременных активных рейсов (инстансов последовательностей) | **300–500** | Соответствует парку среднего-крупного перевозчика + парный учёт нескольких активных последовательностей на борт |
| Латентность приёма (p95) | **< 1000 мс** | Приём — это запись `messages` + публикация `NormalizedEvent` в Outbox; реакция движка (uplink/ground) идёт асинхронно дальше, но сам HTTP-ответ на ACARS-гейтвей должен укладываться в секунду, чтобы не создавать back-pressure на внешний канал |
| Латентность приёма (p99) | **< 2000 мс** | Допуск на хвостовые задержки БД/GC, не более 2x от p95-порога |
| Error rate (HTTP-уровень) | **< 1%** | Жёстче для прод-контура; на дев-стенде 0% — ожидаемо при доступной ёмкости |
| Идемпотентность под конкурентным дублированием | **100%** (`duplicate_response_ok == 1.0`, ровно одна запись `messages`/`NormalizedEvent` на `external_message_id`) | ACARS-гейтвей и реальные авиационные каналы штатно дублируют сообщения (ретраи на земле/в воздухе) — это не пограничный случай, а норма |

Эти же числа закодированы как мягкие `thresholds` непосредственно в скриптах
(`perf/k6/steady-throughput.js`, `ramp-to-degradation.js`: `ingest_latency_ms`:
`p(95)<1000`, `p(99)<2000`, `http_req_failed: rate<0.01`; `duplicate-storm.js`:
`duplicate_response_ok: rate==1.0`).

## 2. Методика

Подробности запуска — `perf/k6/README.md` (не дублируются здесь). Краткая выжимка:

1. Поднять стенд: `docker-compose up --build` из корня репозитория, приложение —
   `http://localhost:8080`.
2. Запустить k6 — либо локальным бинарём, либо через `docker run grafana/k6` (на этой
   машине проверен только Docker-путь, без k6 в PATH; на Windows/Mac Docker Desktop
   обязателен `host.docker.internal` вместо `localhost` в `BASE_URL`, см. `perf/k6/README.md`
   про сетевые нюансы и `MSYS_NO_PATHCONV`).
3. Ключевые env-параметры скриптов: `BASE_URL`, `TARGET_RPS` (steady), `START_RPS`/`MAX_RPS`/
   `STEP_RPS`/`STEP_DURATION` (ramp), `GROUPS`/`COPIES_PER_GROUP`/`ITERATIONS`
   (duplicate-storm), `FLEET_SIZE` (размер пула бортов = число одновременных рейсов),
   `RAW_RATIO` (доля сырых ARINC-сообщений в структурированных сценариях).
4. Результат каждого прогона (`handleSummary`) пишется в `perf/k6/results/*.json` (директория
   в `.gitignore` — артефакты конкретного прогона, не часть исходников). Числа из этих файлов
   переносятся в таблицы ниже вручную, под пометкой об индикативности.

## 3. Сценарии

| Скрипт | Назначение | Executor | Что проверяет |
|---|---|---|---|
| `steady-throughput.js` | Контрольная точка: держит входящий поток на фиксированном `TARGET_RPS` заданное время и снимает latency/error rate без роста нагрузки | `constant-arrival-rate` | Стабильность при постоянной нагрузке — «штатный режим» |
| `ramp-to-degradation.js` | Ступенчато поднимает RPS (`START_RPS` → `MAX_RPS` шагом `STEP_RPS`) до явно избыточного значения, чтобы найти точку, где p95/p99 или error rate резко растут | `ramping-arrival-rate` (темп запросов держится независимо от latency ответа — деградация видна как рост latency/ошибок, а не как тихое снижение фактического RPS) | Точка деградации / запас по throughput |
| `duplicate-storm.js` | Шлёт много одновременных копий одного и того же `externalMessageId` (по `GROUPS` групп × `COPIES_PER_GROUP` VU), повторяя шторм `ITERATIONS` раз | `per-vu-iterations` | Идемпотентность приёма под конкурентной гонкой — каждый повтор должен получить HTTP 200, а не ошибку; фактическое «ровно одна запись в БД на id» скрипт не проверяет сам (это HTTP-контракт-проверка), требует ручной/отдельной SQL-проверки после прогона (`SELECT external_message_id, count(*) FROM messages GROUP BY 1 HAVING count(*) > 1` — ожидается 0 строк) |

Оба сценария throughput бьют по двум эндпоинтам приёма: структурированному
`POST /api/v1/messages/incoming` (P2-1) и сырому `POST /api/v1/messages/incoming/raw`
(P2-2, ARINC 618), в пропорции `RAW_RATIO` (по умолчанию 20% raw). Парк бортов
(`lib/messages.js`) включает демо-борт `VP-BQR`/рейс `SU1234` плюс сгенерированный пул —
каждый VU закреплён за одним бортом/рейсом на весь прогон (1 VU ≈ 1 «активный рейс»).

Примечания:
- `http_req_failed` оставался 0 на всех ступенях — деградация выражается не в HTTP-ошибках,
  а в **росте латентности** и в **`dropped_iterations`** (k6 не успевает поддерживать
  заданный темп исполнителем — сам факт появления `dropped_iterations` с RPS=250 — сигнал,

- На ступени 400 встроенный threshold скрипта `ingest_latency_ms: p(99)<2000` **провалился**
  (`"p(99)<2000": {"ok": false}` — единственный `ok:false` среди всех файлов) — это
  количественное подтверждение деградации, а не только наблюдение по таблице.
- На ступенях 20–220 latency держится в однозначных-двузначных миллисекундах с нулевым error

- Скачок p99 на ступени 200 (221.87 мс) при низком p95 (25.89 мс) — наводит на разовый хвостовой
  выброс (GC-пауза/коннект к БД), не на устойчивую деградацию (на 220 p99 уже ниже — 140.67 мс) —
  не интерпретируем как точку деградации, ступени 250+ дают однозначно растущую картину.

### 4.2 Ramp-to-degradation

В `perf/k6/results/` есть отдельные steady-прогоны на ступенчатых RPS (раздел 4.1), которые
де-факто покрывают тот же диапазон, что должен исследовать `ramp-to-degradation.js`
(10→200+ msg/s). **Файла `ramp-to-degradation-summary.json` в `perf/k6/results/` нет** — отдельный
прогон самого `ramp-to-degradation.js` в этой сессии артефактов не оставил → **TBD** (нужно
прогнать `ramp-to-degradation.js` отдельно; ступенчатые `steady-rps*` числа выше дают
сопоставимую, но не идентичную картину — другой executor (`ramping-arrival-rate` против
`constant-arrival-rate`) и непрерывный, а не дискретный с перезапуском процесса, профиль
нагрузки).

**Точка деградации (по совокупности данных раздела 4.1):** между **220 и 250 msg/s**.
До 220 msg/s включительно — p95 ≤ 25.9 мс, без `dropped_iterations`. С 250 msg/s — p95 уходит
за 400 мс, p99 — за 1.2 с, появляются `dropped_iterations` (104 → 108 → 1479 по ступеням
250/300/400), на 400 msg/s p99 (3.56 с) уже выходит за предлагаемый SLO-порог (`<2000 мс`,
явный `ok: false` в самом скрипте). HTTP error rate при этом всё ещё 0% на всех ступенях —
деградация носит характер растущей очереди/латентности, а не отказов.

### 4.3 Duplicate storm — идемпотентность под конкурентной нагрузкой

Источник: `perf/k6/results/duplicate-storm-summary.json`. Параметры по умолчанию из
скрипта (`GROUPS=20`, `COPIES_PER_GROUP=25` ⇒ 500 VU, `ITERATIONS=5` ⇒ 2500 запросов суммарно,
20 уникальных `externalMessageId`, каждый дублируется 25 одновременными VU × 5 повторов = 125
запросов на id). Прогон занял всего 2.39 с (`testRunDurationMs`) — ожидаемо для
burst-сценария `per-vu-iterations` с 500 VU.

| Метрика | Значение |
|---|---|
| Всего запросов (`http_reqs`/`iterations`) | 2 500 |
| `duplicate_response_ok` (доля HTTP 200 на дубль) | **1.0** (2500/2500, threshold `rate==1.0` → `ok: true`) |
| `http_req_failed` | 0 (0/2500) |
| Checks `"duplicate accepted with 200..."` | 2500 pass / 0 fail |
| `http_req_duration` p50 / p95 / max | 382.6 мс / 781.8 мс / 1503.3 мс |
| `vus_max` | 500 |

**Подтверждение идемпотентности на стороне HTTP-контракта:** да — ни один из 2500 конкурентных
повторов 20 сообщений не получил ничего, кроме HTTP 200 (никаких 4xx/5xx из-за гонки на
уникальном индексе `external_message_id` или конфликте вставки).

**Важная оговорка (явно прописана в самом скрипте, `duplicate-storm.js`, строки 9–16):**
этот прогон проверяет **только клиентскую сторону контракта** — «дубль не вызывает ошибку».
Он **не подтверждает** фактическое «ровно одна запись `messages` и ровно одна публикация
`NormalizedEvent` на `external_message_id`» — для этого после прогона нужен прямой SQL-запрос
к БД (`SELECT external_message_id, count(*) FROM messages GROUP BY 1 HAVING count(*) > 1`,
ожидается 0 строк) и проверка количества инстансов последовательностей на затронутые борты.
**В этой сессии такая SQL-проверка не выполнялась** (стенд не был поднят) — поэтому
содержательная гарантия идемпотентности (а не только «без ошибок по HTTP») — **TBD**, требует
отдельного прогона с проверкой по БД.

## 5. Выводы

1. **Proposed SLO (50–100 msg/s устойчиво, p95<1с, p99<2с, error<1%) на индикативных числах
   выполняется с заметным запасом** — на дев-стенде латентность остаётся в пределах
   единиц-десятков миллисекунд вплоть до ~220 msg/s, что более чем вдвое превышает верхнюю
   границу целевого диапазона.
2. **Индикативная точка деградации — между 220 и 250 msg/s** (рост p95 с ~15–26 мс до ~400 мс,
   p99 — до 1.2+ с, появление `dropped_iterations`; на 400 msg/s p99 уже нарушает предлагаемый
   SLO-порог `<2000 мс`). Запас между верхней границей целевого диапазона (100 msg/s) и
   зафиксированной точкой деградации (~220–250 msg/s) — больше чем 2×, что на первый взгляд
   комфортно, но это **дев-машина одного инженера** (Windows + Docker Desktop), а не
   production-класса инфраструктура — на проде с реальной БД-инфраструктурой и сетевыми
   задержками порог может быть как выше, так и ниже.
3. **Идемпотентность под конкурентной нагрузкой подтверждена только на уровне HTTP-контракта**
   (100% дублей получили 200, без ошибок гонки) — содержательная проверка «ровно одна строка
   в БД на id» не выполнена в этой сессии (нет поднятого стенда) и должна быть отдельным шагом
   перед закрытием уверенности в идемпотентности под нагрузкой.
4. **Точка деградации по `ramp-to-degradation.js` отдельно не подтверждена** — файла
   `ramp-to-degradation-summary.json` в артефактах нет; вывод о точке деградации в этом отчёте
   построен на дискретных ступенчатых `steady-rps*` прогонах (раздел 4.1), что методологически
   близко, но не идентично (другой k6 executor, другой профиль нагрузки — раздельные
   60-секундные плато против непрерывного нарастания). Рекомендация: прогнать
   `ramp-to-degradation.js` отдельно для подтверждения формы кривой деградации одним
   непрерывным прогоном.
5. **Рекомендации по тюнингу** (на случай подтверждения деградации на реальном стенде):
   - Профилировать пул соединений БД (HikariCP) под нагрузкой 250+ msg/s — рост латентности
     без роста error rate типично указывает на очередь к ограниченному пулу подключений или
     на блокировки при записи в `messages`/`event_publication` (Outbox).
   - Проверить наличие узких мест на уникальном индексе `external_message_id` под конкурентной
     записью (duplicate-storm показывает 0 ошибок, но с латентностью p95 ~780 мс на burst —
     для одиночных 20 групп это не критично, но при росте параллелизма дублей может стать
     bottleneck).
   - Рассмотреть батчинг/асинхронную публикацию событий из Outbox, если профилирование покажет,
     что узкое место — синхронная часть приёма, а не сама запись.
6. **Что добавит P5-1 (метрики Prometheus, see `ROADMAP.md` фаза P5)**: этот отчёт построен
   исключительно на клиентских (k6) измерениях — latency «снаружи» и HTTP-статусы. P5-1 даст
   **серверную сторону** замера (пул соединений БД, время обработки по слоям —
   парсинг/персистентность/публикация события/реакция движка, очередь Outbox, GC-метрики JVM),
   что позволит локализовать причину деградации точно (а не предполагать её по форме кривой
   latency снаружи) и построить дашборды для постоянного мониторинга, а не разовых k6-прогонов.
7. **Эти числа — индикативные.** Приёмочный нагрузочный прогон на выделенном стенде
   (production-подобная конфигурация БД/сети, без шумных соседей на хосте, несколько повторов
   для оценки разброса) — отдельная задача, относится к фазе **P6** (`ROADMAP.md`: «Нагрузочное
   тестирование до целевых чисел, профилирование, тюнинг» — `test-engineer`+`perf`). До
   проведения такого прогона proposed SLO раздела 1 и выводы 1–3 этого отчёта не могут считаться
   приёмочно подтверждёнными.
