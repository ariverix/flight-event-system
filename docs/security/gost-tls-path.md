# Путь к ГОСТ TLS для прод-контура (P4-3, проектирование)

Статус: проектирование (design), 2026-06-23. Ответственные: security-agent + devops-agent.

Документ фиксирует ПЛАН перехода прод-контура на TLS с российской криптографией (ГОСТ
Р 34.10-2012 / 34.11-2012, шифрсюиты ГОСТ для TLS 1.2/1.3 по РФ-профилям). Реализация —
при развёртывании прод-контура (после P8-1 Helm), здесь — обоснованный путь, не код.

## Контекст и требования

- Импортозамещение (CLAUDE.md): стек пригоден для Реестра российского ПО, путь к ГОСТ TLS
  для прод-контура, без жёсткой привязки к зарубежной проприетарщине.
- Текущее состояние: приложение слушает HTTP (`server.port=8080`); TLS-терминация не
  настроена (предполагается на уровне инфраструктуры). JWT-секрет и пароли уже вынесены в
  окружение (см. secrets-management.md).
- ФСТЭК/регуляторика: защита канала «оператор ↔ система» и «система ↔ внешние шлюзы» должна
  допускать сертифицированные СКЗИ.

## Целевая архитектура (рекомендованный вариант)

**ГОСТ-TLS терминируется на отечественном reverse-proxy перед приложением**, приложение
остаётся на обычном HTTP/JWT внутри доверенного периметра.

```
Оператор/внешний шлюз --[ГОСТ TLS]--> [reverse-proxy с ГОСТ-СКЗИ] --[HTTP, mTLS/loopback]--> eca-app:8080
```

- Reverse-proxy: Angie/nginx со сборкой с ГОСТ-движком OpenSSL (gost-engine) ИЛИ
  сертифицированный ФСТЭК/ФСБ шлюз (КриптоПро NGINX / С-Терра и аналоги).
- Сертификаты: ГОСТ Р 34.10-2012 от аккредитованного УЦ; ключи в сертифицированном СКЗИ
  (КриптоПро CSP / ViPNet / аппаратный HSM с поддержкой ГОСТ).
- Внутренний хоп proxy→app: в пределах пода/узла (loopback) либо mTLS; приложение не
  занимается ГОСТ-криптографией само (JVM штатно ГОСТ-сюиты не умеет — выносим в proxy).

### Почему терминация на proxy, а не в JVM

- JCE/JSSE из коробки не поддерживает ГОСТ-сюиты; интеграция ГОСТ-провайдера в JVM
  (например, через JCP/КриптоПро Java CSP) возможна, но усложняет сборку и сертификацию
  каждого артефакта. Терминация на специализированном сертифицированном прокси — стандартный
  и проверяемый путь, изолирует крипто от бизнес-кода.

## Альтернатива (если требуется ГОСТ внутри JVM)

КриптоПро Java CSP как JCE-провайдер + настройка Tomcat connector на ГОСТ-сюиты. Минусы:
лицензирование на каждый узел, сложнее CI-сборка и обновления JDK. Рассматривать, только
если периметр требует ГОСТ end-to-end до самого приложения.

## Что нужно сделать при внедрении (чек-лист, не сейчас)

1. Выбрать сертифицированное СКЗИ/прокси под контур заказчика (согласовать с ФСТЭК-профилем).
2. Выпустить ГОСТ-сертификаты через аккредитованный УЦ; хранить ключи в СКЗИ/HSM.
3. Helm (P8-1): sidecar/ingress с ГОСТ-TLS; секреты сертификатов — через secret-manager.
4. mTLS/allowlist на пути приёма ACARS (эндпоинт `/api/v1/messages/**` открыт по JWT, но
   защищён сетево — это осознанное решение, CLAUDE.md п.7); рассмотреть ГОСТ-mTLS и здесь.
5. Приёмочные тесты канала с ГОСТ-сюитами (curl с gost-engine / стенд заказчика).

## Вне объёма P4-3

Сама установка СКЗИ, выпуск сертификатов и настройка прокси — этап развёртывания прод-контура.
Здесь зафиксирован путь и решения; код приложения для этого менять не требуется (TLS — на
инфраструктуре).
