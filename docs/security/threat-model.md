# Threat model (черновик) — flight-event-system

**Статус:** черновик P0-6 (RUN_PLAN.md). Подлежит пересмотру на каждой фазе P1–P5,
особенно после P2-1 (входящий ACARS-шлюз), P4-1..P4-5 (RBAC/JWT/секреты/сканы/аудит).
Owner: security-agent. Дата создания: 2026-06-19.

## 1. Краткое описание системы

ECA-система обрабатывает авиационные события по сообщениям «борт-земля» (ACARS):
принимает входящие сообщения от внешних бортовых/наземных систем, прогоняет их через
движок правил (последовательности шагов ACTION/EVALUATE IF/WAIT FOR), отправляет
исходящие uplink/ground-сообщения, хранит состояние рейсов/последовательностей в
PostgreSQL. Пользователи (диспетчеры/администраторы) управляют последовательностями,
шаблонами, правами через защищённый JWT REST API и веб-UI.

Backend: Java 21 / Spring Boot 3.5 / Spring Modulith, модули `sequence`, `execution`,
`eventprocessor`, `integration`, `user`. БД: PostgreSQL 16 (Flyway-миграции V1–V20).

## 2. Доверенные границы (trust boundaries)

| # | Граница | Описание |
|---|---|---|
| TB-1 | Внешняя бортовая/наземная система → `/api/v1/messages/**`, `/api/v1/flights/**` | Открытый ingestion-эндпоинт ACARS, **без JWT**. Источник недоверенный по содержимому, доверенный по факту сетевого расположения (предполагается отдельный защищённый сегмент/канал). |
| TB-2 | Пользователь/администратор (браузер/UI) → защищённое REST API | JWT Bearer, RBAC по ролям (ADMIN/OPERATOR), проверка на уровне `SecurityConfig` + `@PreAuthorize`. |
| TB-3 | Backend → PostgreSQL | Внутренний сегмент, доверенный канал (БД не выставлена наружу), но содержит чувствительные данные (хэши паролей, аудит, бизнес-данные рейсов). |
| TB-4 | Backend → исходящие каналы uplink/ground (внешние получатели) | Исходящий поток ACARS uplink и ground-сообщений по командам движка (ACTION send uplink/ground). На сегодня не реализован (см. P2-3) — граница учтена на будущее. |
| TB-5 | Backend → Swagger UI / OpenAPI (`/v3/api-docs`, `/swagger-ui/**`) | Сейчас `permitAll` без ограничения по окружению — потенциальная утечка структуры API в проде. |
| TB-6 | Backend → Actuator (`/actuator/**`) | `health` — `permitAll`; остальное — `hasRole("ADMIN")`. |

## 3. STRIDE по ключевым точкам входа

### 3.1 Открытый ACARS-эндпоинт (`/api/v1/messages/incoming`, `/api/v1/flights/stage-change`) — TB-1

| STRIDE | Угроза | Текущий статус | Митигирование / фаза |
|---|---|---|---|
| **S**poofing | Любой узел с сетевым доступом может представиться бортом/наземной системой (нет аутентификации на уровне приложения) | **Open risk** | Компенсирующий контроль — сетевой (mTLS клиентских сертификатов и/или IP allowlist, отдельный сетевой сегмент/VLAN для интеграции с борт-системами). Осознанное архитектурное решение (см. CLAUDE.md, п.7 рабочего протокола). Сетевой контроль — зона devops-agent/инфраструктуры заказчика, не прикладной код. Зафиксировать в проектной документации по развёртыванию (P8-1/инфраструктура заказчика). |
| **T**ampering | Подмена содержимого ACARS-сообщения (payload, борт, рейс) в пути или на источнике | **Open risk**, частично снижается TLS на транспорте | TLS обязателен на этом пути (см. §5). Целостность payload на уровне сообщения (подпись/контрольная сумма ARINC) — не в скоупе P0, оценить в P2-2 при разборе форматов ARINC 620/618. |
| **R**epudiation | Источник может отрицать отправку сообщения (нет аутентификации отправителя) | **Open risk** | Частично смягчается логированием (correlationId, IP отправителя, timestamp в `IncomingMessage`/логах). Полноценная неотрекаемость требует TB-1 аутентификации источника (mTLS с клиентским сертификатом) — см. п. mTLS выше. |
| **I**nformation disclosure | Ответ эндпоинта или логи могут раскрыть внутренние детали (stack trace, structure) | **Mitigated** (частично) | Единый `@ControllerAdvice` нормализует ошибки; structured JSON-логи (P0-4) не печатают исходный нефильтрованный ввод как часть сообщения лога без структурирования полей. Требует точечной проверки на этапе P2-1/P2-2 (логирование payload входящих сообщений целиком может содержать ПДн/чувствительные коммерческие данные рейса — нужна политика маскирования). |
| **D**enial of service | Эндпоинт без аутентификации = открыт для флуда запросами | **Mitigated** | Rate limiting реализован (bucket4j, `RateLimitFilter`, прогон «Промышленный апгрейд» 2026-07-03): per-IP токен-бакет на `/api/v1/messages/**` (потолок настраивается, дефолт 2000 req/s — выше штатного пика ~375 msg/s, режет только runaway-флуд), 429 RFC7807 + метрика `eca.ratelimit.rejected`. XFF учитывается только от доверенных прокси (`app.ratelimit.trusted-proxies`), карты бакетов ограничены LRU. Дополняется сетевым allowlist/mTLS. |
| **E**levation of privilege | Через open-эндпоинт нельзя получить привилегии в защищённой части API — эндпоинт изолирован по `requestMatchers`, не имеет доступа к ADMIN/OPERATOR функциям напрямую | **Mitigated** | Эндпоинт ограничен своей зоной ответственности (приём сообщений), не предоставляет CRUD по последовательностям/пользователям. Подтверждено код-ревью `SecurityConfig`. |
| Дополнительно: **идемпотентность** | Повторная отправка одного и того же сообщения (retry со стороны борта/сети) может вызвать дублирование обработки и побочных эффектов (повторный uplink, ложные условия) | **Open / planned** | Идемпотентность по идентификатору сообщения с persist раньше обработки — запланирована в P2-1 (RUN_PLAN.md). На сегодня `EventProcessorService.receiveMessage` не делает дедупликацию по бизнес-ключу сообщения. |

### 3.2 Защищённое REST API (JWT + RBAC) — TB-2

| STRIDE | Угроза | Текущий статус | Митигирование / фаза |
|---|---|---|---|
| **S**poofing | Подмена/кража JWT (XSS, перехват токена) | Частично mitigated | JWT передаётся в Authorization header (не в cookie — снижает CSRF-поверхность); CORS ограничен явным allowlist origin (`localhost:5173/3000` — **требует обновления под прод-домен заказчика**, см. примечание в §5). XSS-защита — на стороне React (без `dangerouslySetInnerHTML` и т.п.) не аудирована в рамках P0-6 — отдельная проверка фронтенда. |
| **T**ampering | Подмена payload запроса администратора/оператора | Mitigated | Bean Validation (`@Valid`) на DTO входа; контроллеры не доверяют клиентским ID напрямую без проверки владения/прав (точечно не аудировано по каждому эндпоинту — зона P4-1). |
| **R**epudiation | Действие пользователя (логин, изменение последовательности/прав) не может быть прослежено к конкретному пользователю/времени | **Частично mitigated** | `audit_log` (V7, V20) уже пишет события логина и изменений последовательностей через `AuditLogPort`/`AuditLogJpaAdapter` (см. `user`/`sequence` модули) с `correlation_id`. Полнота покрытия всех чувствительных действий (изменение прав/ролей, CRUD пользователей и т.д.) — предмет верификации в **P4-5** ("Полный audit_log действий пользователя"). На сегодня это частичная, не полная реализация. |
| **I**nformation disclosure | Эндпоинт `/api/v1/auth/me`, ошибки аутентификации могут раскрывать данные пользователей | Mitigated (базово) | `401` через единый `HttpStatusEntryPoint`, нет различия "пользователь не найден" vs "неверный пароль" в ответе (не проверено отдельно — рекомендация на ревью P4-1/P4-2). |
| **D**enial of service | Brute-force на `/api/v1/auth/login` | **Mitigated** | Rate limiting реализован (bucket4j, `RateLimitFilter`): per-IP лимит на `/api/v1/auth/login|refresh|logout` (дефолт 10 попыток/60c), 429 + метрика. Фильтр стоит ПЕРЕД аутентификацией. Account lockout (в дополнение к rate limiting) — возможный follow-up. |
| **E**levation of privilege | Эскалация роли через подмену claim в JWT, либо через "дыры" в матчерах `SecurityConfig` | **Open risk — архитектурный, идентифицирован при ревью** | См. отдельный пункт §4 ниже (`anyRequest().permitAll()`). JWT claims подписаны (HMAC, см. `JwtService`/`jjwt`) — подмена без знания секрета невозможна, но **секрет на сегодня хардкожен в `application.yml`** (см. §5) — при компрометации секрета возможна полная эскалация (подделка токена с любой ролью). |

## 4. Архитектурный риск: default-allow в `SecurityConfig`

Цепочка матчеров `SecurityConfig.securityFilterChain()` заканчивается на:

```java
.anyRequest().permitAll()
```

**Это default-allow, а не default-deny.** Любой новый эндпоинт, добавленный без явного
`requestMatchers(...)` правила, **по умолчанию открыт без аутентификации**, а не закрыт —
что прямо противоречит правилу проекта «деградация прав запрещена» (CLAUDE.md, «Жёсткие
правила») и общепринятому принципу secure-by-default.

- **Текущий статус:** Open risk, идентифицирован реviewer'ом ранее (зафиксировано в
  постановке P0-6).
- **Почему не исправлено сейчас:** изменение прикладной security-логики выходит за рамки
  P0 (каркас/документация) и относится к **P4-1** (RBAC user-rights, роли→права→проверки
  на эндпоинтах). Исправление до P4-1 без полной модели прав рискует точечными патчами
  без системного покрытия.
- **План митигирования:** в рамках **P4-1** переписать цепочку на explicit default-deny
  (`.anyRequest().authenticated()` или `.anyRequest().denyAll()` с точечными `permitAll`
  только для явно перечисленных публичных путей — auth/login, ACARS ingestion, Swagger по
  профилю, actuator/health), и добавить architecture-тест (по аналогии с
  `ApplicationModules.verify()`), фейлящий сборку при отсутствии явного правила для нового
  пути. Зона ответственности: security-agent + db-dev (для PERMISSION/ROLE моделей).
- **Компенсирующий контроль до P4-1:** код-ревью каждого нового контроллера/эндпоинта
  обязано явно проверять соответствующее правило в `SecurityConfig` (см. CLAUDE.md,
  «Жёсткие правила»: «новый эндпоинт без явной проверки прав не принимается»).

## 5. Секреты и криптография

| Угроза | Текущий статус | Митигирование / фаза |
|---|---|---|
| Секрет подписи JWT (`app.jwt.secret`) хардкожен в `backend/src/main/resources/application.yml` | **Open risk** | Вынос в env/secret manager — **P4-3**. До этого секрет одинаков во всех средах, где используется этот файл «as is» — критично заменить перед любым прод-окружением. |
| Креды БД (`eca_user`/`eca_password`) хардкожены в `application.yml` и `docker-compose.yml` | **Open risk, известный и принятый для dev/демо-контура** | Допустимо для локальной разработки (`admin/admin`-уровня риск, см. CLAUDE.md: «Никаких дефолтных паролей в прод-конфиге (admin/admin только локально для разработки)»). Для прод — вынос в secret manager, ротация — **P4-3**. |
| Демо/дефолтный администратор (`admin/admin`, V8 миграция) | **Known, by design for dev** | Недопустим в прод-конфиге согласно CLAUDE.md. Контроль на старте прод-развёртывания — проверить, что V8 не создаёт дефолтного админа в прод-профиле / либо пароль форсированно меняется при первом входе. Зона P4-3/P8 (деплой-чеклист заказчика). |
| Транспорт: TLS наружу | **Planned/partial** | HTTPS наружу — требование CLAUDE.md/задачи. Путь к ГОСТ TLS (ГОСТ-шифрсьюты, отечественные криптопровайдеры, напр. КриптоПро) для прод-контура заказчика — отдельный архитектурный путь, ADR по криптографии — **P4-2/P4-3** (см. постановку «ADR по токенам/крипто»). На сегодня уровень TLS — стандартный (TLS termination на уровне reverse proxy/ingress в целевой инфраструктуре, не реализовано в текущем коде приложения). |
| BCrypt для паролей пользователей | **Mitigated** | `BCryptPasswordEncoder` подключён в `SecurityConfig` — соответствует требованию. |

## 6. Прочие точки, учтённые в скоупе P0-6

| Угроза | Текущий статус | Митигирование / фаза |
|---|---|---|
| Log injection / log forging через `X-Correlation-Id` | **Mitigated** (P0-4) | `CorrelationIdFilter` валидирует входящий заголовок по строгому whitelist `^[A-Za-z0-9-]{1,64}$`; при несоответствии — генерируется новый UUID, исходное значение полностью отбрасывается (не очищается построчно). Закрыто. |
| Уязвимости в зависимостях (CVE) | **Planned** | OWASP Dependency-Check — **P4-4**, фейл сборки на High/Critical. License report зависимостей — частично закрывается в этом тикете (P0-6), см. `docs/security/fstec-checklist.md` и CI-шаг license-report (информационный, не блокирующий). |
| SAST (статический анализ кода на уязвимости) | **Planned** | Semgrep/SpotBugs+FindSecBugs — **P4-4**. |
| Утечка чувствительных данных в логи (payload сообщений, ПДн, пароли) | **Частично проверено** | Структурные JSON-логи (P0-4) не выводят пароли/секреты в явном виде в проверенных местах (`AuthController`, `JwtService` не логируют сырые пароли/токены). Полный аудит всех `log.*` вызовов на чувствительные данные — не проведён системно в рамках P0-6, рекомендуется точечный grep-чеклист перед релизом (`password`, `secret`, `token` в формате логов) — кандидат на правило SAST в P4-4. |

## 8. Закрытые/смягчённые на сегодня

- Log injection через correlationId — closed (P0-4, whitelist-валидация).
- Пароли пользователей — BCrypt, не plaintext — mitigated.
- Эскалация привилегий через open ACARS-эндпоинт напрямую в защищённый CRUD — mitigated
  (эндпоинт изолирован своей зоной, не даёт доступа к административным операциям).
- SQL injection — mitigated по дизайну (JPA/параметризованные запросы), системная проверка
  — SAST в P4-4.
