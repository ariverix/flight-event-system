# Чек-лист требований ФСТЭК (черновик) — flight-event-system

**ВАЖНО — статус документа:** это рабочий черновик, составленный инженером ИБ по смыслу
типовых мер защиты информации (применимых к ИС, обрабатывающим информацию ограниченного
доступа/защищаемую информацию в государственном секторе), а **не** юридически выверенная
сверка с конкретными приказами ФСТЭК России. Номера приказов, точные классы защищённости
ГИС/ИСПДн и обязательность конкретных мер **требуют отдельной верификации с
compliance/юристом заказчика (ФГУП «ЗащитаИнфоТранс»)** до использования документа как
основания для аттестации/сертификации. Цель черновика — дать инженерную базу: что уже
есть в системе, что частично, что отсутствует, чтобы compliance мог сопоставить с
формальными требованиями (предположительно семейство приказов ФСТЭК по защите информации
в государственных информационных системах и/или значимых объектах КИИ — конкретная
применимость зависит от категорирования системы заказчиком, что вне зоны ответственности
этого тикета).

Owner: security-agent + compliance-agent. Дата: 2026-06-19. Пересмотр: после P4 (RBAC/JWT/
секреты/сканы/аудит) и перед P8-3 (материалы для Реестра российского ПО).

Условные обозначения статуса:
- **Есть** — реализовано и проверено (тестами/код-ревью).
- **Частично** — реализовано, но не покрывает требование полностью.
- **Нет** — не реализовано.
- **Планируется (Pxx)** — запланировано в конкретной фазе RUN_PLAN.md.

## 1. ИАФ — Идентификация и аутентификация субъектов доступа

| Требование (по смыслу меры) | Статус | Комментарий |
|---|---|---|
| Идентификация и аутентификация пользователей при логическом доступе к системе | Есть | JWT-аутентификация (`/api/v1/auth/login`), `JwtAuthenticationFilter`, `SecurityConfig`. |
| Управление идентификаторами пользователей (создание/блокировка/удаление учётных записей) | Частично | CRUD пользователей есть (`/api/v1/users/**`, ADMIN-only), но нет явного процесса деактивации/блокировки учётной записи при увольнении/смене роли — требует проверки в `UserService`. |
| Управление средствами аутентификации (хранение, генерация, смена паролей) | Частично | Пароли хранятся как BCrypt-хэш (не plaintext) — соответствует общей мере. Политика сложности паролей, принудительная смена при первом входе, история паролей — не реализованы. |
| Защита обратной связи при вводе аутентификационных данных (например, не показывать пароль в открытом виде) | Не аудировано на фронтенде | Зона ответственности фронтенда, не входит в backend-аудит P0-6. |
| Идентификация и аутентификация внешних систем (взаимодействие borт-земля) | Нет (осознанно, компенсируется сетевым контролем) | Открытый ACARS-эндпоинт без аутентификации на уровне приложения — компенсирующий контроль mTLS/IP allowlist на сетевом уровне (см. `docs/security/threat-model.md`, TB-1). Это явное архитектурное решение проекта (CLAUDE.md, п.7), а не пробел. |
| Защита от подбора пароля (lockout/rate limiting) | Да (rate limiting) | Rate limiting реализован (bucket4j `RateLimitFilter`, прогон 2026-07-03): per-IP лимит на `/auth/login` (дефолт 10/60c) перед аутентификацией, 429 + метрика. Account lockout — возможный доп. контроль (follow-up). См. R-4. |
| Многофакторная аутентификация (если требуется классом защищённости) | Нет, не оценено | Применимость зависит от класса защищённости/категории информации — требует решения compliance. |

## 2. УПД — Управление доступом субъектов к объектам доступа

| Требование | Статус | Комментарий |
|---|---|---|
| Управление учётными записями (создание ролей, назначение прав) | Частично | Роли ADMIN/OPERATOR заданы (`Role` enum), но детальная модель прав по образцу SITA user rights («Manage sequences», «edit Aircraft» и т.п.) — **планируется в P4-1**. |
| Реализация модели разграничения доступа (RBAC) на основе ролей | Частично | Базовый RBAC есть на уровне ролей ADMIN/OPERATOR, но не на уровне детальных прав/permission. Полная модель — P4-1. |
| Доверенная загрузка / ограничение программной среды | Не применимо на уровне приложения | Зона инфраструктуры (P8-1, целевой контур заказчика). |
| Управление установкой/обновлением ПО | Частично | CI/CD каркас есть (P0-1), управляемый деплой через Helm — планируется P8-1. |
| Изоляция процессов (среды исполнения) | Частично | Docker-изоляция контейнеров есть; Kubernetes/неймспейсы — планируется P8-1. |
| Защита беспроводных соединений | Не применимо | Не используется в текущей архитектуре. |
| Регламентация и контроль использования технологий беспроводного доступа | Не применимо | — |
| **Принцип "запрещено по умолчанию" (default-deny) на уровне API** | **Нет — известный риск** | `SecurityConfig` заканчивается `.anyRequest().permitAll()` — default-allow. Идентифицировано как открытый риск R-1 в threat model, митигируется в **P4-1**. |
| Управление информационными потоками между сегментами/компонентами | Частично | Модульная граница на уровне Spring Modulith (`ApplicationModules.verify()` в CI), но сетевая сегментация (борт-системы / пользовательский сегмент / БД) — зона инфраструктуры заказчика, не код. |

## 3. РСБ — Регистрация событий безопасности (аудит)

| Требование | Статус | Комментарий |
|---|---|---|
| Регистрация событий входа/выхода пользователей в систему | Частично | `audit_log` пишет события логина через `AuditLogPort`/`AuditLogJpaAdapter` (модуль `user`). Событие logout/инвалидация токена — зависит от реализации refresh-инвалидации, **P4-2**. |
| Регистрация событий управления учётными записями и правами доступа | Нет/планируется | CRUD пользователей и изменение ролей — полное покрытие аудитом запланировано в **P4-5** («Полный audit_log действий пользователя — логин, изменение последовательности/прав»). |
| Регистрация событий доступа к защищаемой информации (изменение последовательностей, шаблонов и т.п.) | Частично | Изменения последовательностей пишутся в `audit_log` (модуль `sequence`, `AuditLogJpaAdapter`). Полнота по всем сущностям — не верифицирована построчно, нужен чек-лист по каждому write-эндпоинту перед P4-5 done. |
| Защита аудиторской информации от несанкционированного доступа/модификации | Частично | `/api/v1/audit-log/**` ограничен ADMIN-ролью. Защита от модификации на уровне БД (например, append-only/триггеры запрета UPDATE/DELETE) — не реализована, кандидат на доработку при P4-5. |
| Корреляция событий аудита со структурными логами | Есть | `correlation_id` в `audit_log` (V20) + сквозной `CorrelationIdFilter`/MDC (P0-4) — позволяет связать запись аудита с конкретным HTTP-запросом/логами. |
| Хранение и ротация журналов аудита (retention) | Нет/планируется | Партиционирование/retention больших таблиц (event log, audit) по времени — запланировано в **P6-2**. |
| Мониторинг и реагирование на события безопасности (алертинг по аномалиям) | Нет/планируется | Дашборды/алерт-правила — **P5-3**. |

## 4. ОЦЛ — Обеспечение целостности

| Требование | Статус | Комментарий |
|---|---|---|
| Контроль целостности программного обеспечения и конфигурации | Частично | Версионирование через Maven/git, миграции Flyway версионируемые и неизменяемые после применения (правило проекта — CLAUDE.md, п.3). Формальный контроль целостности (например, подписи артефактов сборки) — не реализован. |
| Контроль целостности данных (защита от непреднамеренного/преднамеренного искажения) | Частично | Bean Validation на входных DTO, БД-констрейнты (Flyway-схема). Контрольные суммы/подписи входящих ACARS-сообщений — не реализованы, кандидат на оценку в P2-2 (разбор ARINC 620/618). |
| Обеспечение возможности восстановления ПО и данных после сбоев | Нет/планируется | Бэкап/восстановление БД (pg_dump/PITR) + тест восстановления — **P5-4**. |
| Контроль состава и целостности зависимостей (supply chain) | Частично/планируется | License report зависимостей — добавляется этим тикетом (P0-6, информационно). Сканирование на CVE (OWASP Dependency-Check) — **P4-4**. Контроль целостности артефактов из репозиториев Maven Central (checksums) — обеспечивается стандартным механизмом Maven, отдельно не усилен. |

## 5. Защита среды виртуализации/контейнеров

| Требование | Статус | Комментарий |
|---|---|---|
| Изоляция контейнеров приложения и БД | Есть (базовый уровень) | Docker Compose с раздельными контейнерами `app`/`postgres`, без общих namespace. |
| Управление образами (минимизация, сканирование образов на уязвимости) | Нет/планируется | Сканирование образов (Trivy/аналог) — не входит явно в текущий RUN_PLAN, рекомендуется добавить в рамках P4-4 (расширение скоупа) или отдельным пунктом перед P8-1. |
| Защита оркестрации (Kubernetes RBAC, NetworkPolicy, Pod Security) | Нет/планируется | Kubernetes/Helm чарты — **P8-1**, должны включать NetworkPolicy между сегментами (особенно изоляция ingestion ACARS от остального кластера) и Pod Security Standards. |
| Секреты в оркестраторе (Kubernetes Secrets / внешний secret manager) | Нет/планируется | Сейчас секреты в `application.yml`/`docker-compose.yml` (см. threat model R-2). Вынос — **P4-3**, интеграция с K8s Secrets/Vault-подобным механизмом — уточнить при P8-1. |

## 6. Криптографическая защита

| Требование | Статус | Комментарий |
|---|---|---|
| Шифрование канала передачи данных (TLS) для пользовательского/административного трафика | Планируется | HTTPS наружу — требование CLAUDE.md. Текущая конфигурация — без TLS termination в коде приложения (предполагается на уровне reverse proxy/ingress целевой инфраструктуры). Подлежит явной настройке перед прод-эксплуатацией. |
| Шифрование канала для интеграционного (ACARS) трафика | Планируется | TLS/mTLS для открытого эндпоинта — компенсирующий контроль из threat model (TB-1, R-3). |
| **Применение сертифицированных СКЗИ / ГОСТ-алгоритмов** (для информации, требующей криптографической защиты по требованиям заказчика) | Нет — требует архитектурного решения | Путь к ГОСТ TLS (ГОСТ-шифрсьюты, отечественные криптопровайдеры, например через интеграцию с КриптоПро CSP или совместимый стек) для прод-контура заказчика — отдельная задача, ADR по криптографии запланирован в рамках **P4-2/P4-3**. Применимость сертифицированных СКЗИ (обязательность для конкретного контура заказчика) — **требует юридической верификации** с заказчиком/регулятором, не определяется инженером самостоятельно. |
| Защита паролей при хранении (хэширование) | Есть | BCrypt (`BCryptPasswordEncoder`). |
| Защита JWT (подпись, алгоритм) | Частично | HMAC-подпись через `jjwt`, но секрет хардкожен в конфиге (см. R-2) — критично для устойчивости подписи к компрометации. Вынос секрета — P4-3; пересмотр алгоритма/длины ключа — кандидат на ADR в P4-2. |

## 7. Дополнительно: организационные меры (вне кода, для compliance)

| Требование | Статус | Комментарий |
|---|---|---|
| Модель угроз и модель нарушителя (формальная, по методике ФСТЭК) | Черновик | `docs/security/threat-model.md` — инженерный черновик STRIDE, не заменяет формальную модель угроз/нарушителя по методическим документам ФСТЭК. Требуется доработка compliance-agent/внешним консультантом. |
| Категорирование объекта (КИИ) / класс защищённости ГИС / уровень защищённости ИСПДн | Не определено | Зависит от решения заказчика (ФГУП) о категории обрабатываемой информации и объекта КИИ — вне технической зоны ответственности этого тикета. Все статусы выше нужно сопоставить с конкретным классом после категорирования. |
| Регламенты эксплуатации, реагирования на инциденты, резервного копирования | Частично/планируется | Ранбуки эксплуатации — **P8-2**. |
| Включение в Реестр российского ПО | Планируется | Материалы — **P8-3**. Лицензионная чистота зависимостей (license report) — первый шаг в этом тикете (P0-6), полная политика допустимых лицензий — зона compliance перед P8-3. |
