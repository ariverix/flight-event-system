# ADR-0008: Переход на Spring Boot 4.x / Spring Framework 7.x / Spring Security 7.x

**Status:** Proposed

**Date:** 2026-09-02

**Authors:** claude session (по запросу Дениса, после разбора серии CVE на EOL-ветке), architect — на ревью

## Context

Стек проекта запинен на Spring Boot 3.5.16 (CLAUDE.md: "Стек — не менять без ADR архитектора").
Это последний OSS-релиз линии 3.5.x — линия объявлена EOL 30 июня 2026. Синхронно с ней
Spring Framework 6.2.x и Spring Security 6.5.x также вошли в EOL: патчи для уязвимостей,
найденных после этой даты, публикуются ТОЛЬКО через платную Enterprise Support подписку
(VMware/Broadcom) — в открытый Maven Central они не попадают.

За последние две недели (по состоянию на 2026-09-02) на пин-версии проекта найдено 5
критических/высоких CVE без открытого патча:

| CVE | Компонент | CVSS (NVD) | Фикс | Доступность |
|---|---|---|---|---|
| CVE-2026-59313 | spring-web/core 6.2.19 (SSE spoofing) | 9.8 (вендор: 2.6) | — | Только Enterprise |
| CVE-2026-47892 | spring-web/core 6.2.19 (WebFlux header bypass) | 9.8 | 6.2.20 | Только Enterprise |
| CVE-2026-47893 | spring-web/core 6.2.19 (WebFlux header leak) | 7.5 | — | Нет фикса для 6.2.x вообще |
| CVE-2026-59283 | spring-web/core 6.2.19 (SpEL compiler bypass) | 9.1 | 6.2.20 | Только Enterprise |
| CVE-2026-59270 | spring-security-{core,web} 6.5.11 (embedded LDAP) | 9.1 | 6.5.12 | Только Enterprise |

Все пять подавлены точечно в `backend/owasp-suppressions.xml` с обоснованием, что конкретный
уязвимый код-путь не задействован в проекте (WebFlux/SpEL/embedded LDAP — не используются;
проект на Spring MVC + STOMP WebSocket, JWT+BCrypt-аутентификация, без SpEL-вычислений).
Это рабочая, но НЕ масштабируемая стратегия: каждая новая находка на EOL-ветке требует
ручного анализа применимости, и нет гарантии, что ВСЕ будущие находки окажутся так же
безопасно неприменимыми — рано или поздно появится CVE, которую честно не обосновать
как false-positive для данного проекта, и она станет блокирующей, а не плановой.

Единственный бесплатный (OSS) путь получения патчей — переход на линию Spring Framework 7.x /
Spring Security 7.x, т.е. Spring Boot 4.x (GA 30 ноября 2025).

**Технические предпосылки, проверенные на текущий момент:**
- Java-бейзлайн проекта — 21 (`java.version` в `pom.xml`). Spring Boot 4 требует минимум
  Java 17, Framework 7 полностью поддерживает Java 25 — апгрейда JDK не требуется.
- **Spring Modulith** (межмодульные события, Transactional Outbox — ADR-0002/ADR-0007) запинен
  на 1.3.1, совместим только с линией Boot 3.x (ветка 1.4.x — последняя, поддерживающая
  Boot 3.5). Переход на Boot 4 требует Modulith 2.0+, который **меняет схему таблицы
  `event_publication`** (добавляет три новые колонки, переработан жизненный цикл публикации
  событий). Это напрямую задевает:
  - `BaseIntegrationTest.resetDatabase()` — вручную пересоздаёт `event_publication` после
    `flyway.clean()` (таблица создаётся Hibernate DDL, не Flyway) — SQL пересоздания придётся
    синхронизировать с новой схемой Modulith 2.x.
  - ADR-0002 (Outbox vs прямой вызов) и ADR-0007 (dedup через UNIQUE-индекс) — оба построены
    на текущей семантике `event_publication`, нужен явный ревью на совместимость с новым
    жизненным циклом публикации.
- Jakarta EE 11 / Servlet 6.1: Boot 4 роняет поддержку Undertow (не используется в проекте —
  встроенный Tomcat, не риск); требует финального перехода `javax.*` → `jakarta.*` там, где
  ещё остался `javax` в транзитивных зависимостях (JWT-библиотека `jjwt`, `springdoc-openapi`,
  `bucket4j` — версии, зафиксированные под Boot 3.5, нужно проверить на актуальность под
  Framework 7 при планировании).

## Decision

Мы **не переходим** на Spring Boot 4.x немедленно. Настоящий ADR фиксирует это как явное,
осознанное решение отложить миграцию до отдельного спланированного апгрейд-эпика — а не
реактивный факап на очередной CVE. До момента миграции официальная стратегия — принятие
риска по каждой находке индивидуально через `owasp-suppressions.xml` (см. существующие блоки
CVE-2026-59313/47892/47893/59283/59270), с обязательным обоснованием неприменимости
конкретного кода-пути.

**Триггеры пересмотра (любой из них — повод начать миграцию как приоритетную задачу):**
1. Появление CVE на пиновой линии (Framework 6.2.x / Security 6.5.x), которую **нельзя** честно
   обосновать как неприменимую в этом проекте (т.е. уязвимый код-путь реально используется).
2. Явное решение архитектора/Дениса заложить миграцию как отдельный эпик в `ROADMAP.md`.
3. Плановый срок: не позднее конца Q1 2027, если ни один из триггеров 1–2 не сработает раньше —
   риск подавления множащихся EOL-CVE к этому моменту накопится настолько, что дальнейшая
   отсрочка станет неоправданной вне зависимости от конкретных находок.

**Объём будущей миграции** (для планирования эпика — НЕ выполняется в рамках этого ADR):
1. Bump родительского POM на `spring-boot-starter-parent` 4.x — компиляция, разбор
   deprecation/breaking changes Framework 7 / Security 7.
2. Spring Modulith 1.3.1 → 2.x: новая Flyway-миграция (V40+) на схему `event_publication`
   (три новые колонки), обновление ручного пересоздания таблицы в `BaseIntegrationTest`, ревью
   ADR-0002/ADR-0007 на совместимость с новым жизненным циклом публикации событий.
3. Аудит транзитивных зависимостей на `javax.*` → `jakarta.*` (Jakarta EE 11/Servlet 6.1):
   `jjwt`, `springdoc-openapi`, `bucket4j` и др. — актуальные версии под Framework 7.
4. Полный verification loop (923+ backend, 282+ frontend, E2E, JaCoCo-гейт, Modulith verify)
   — на порядок выше риск регрессий, чем при обычной фиче; вертикальный срез здесь не
   применим буквально, апгрейд неделим по своей природе.
5. После зелёного прогона — снять более неактуальные suppression'ы CVE-2026-59313/47892/
   47893/59283/59270 из `owasp-suppressions.xml` (риски устранены самой версией, не обходом).

Границы модулей не меняются — это upgrade инфраструктурного слоя (parent POM, вспомогательные
библиотеки), не архитектурное решение о модулях/событиях как таковое.

## Consequences

**Положительные (после будущей миграции):**
- Возврат в OSS-патчируемую линию — новые CVE снова закрываются бесплатными патчами вместо
  ручного анализа применимости на каждую находку.
- Framework 7 / Boot 4 — актуальная поддерживаемая линия на годы вперёд (снимает риск
  повторного попадания на EOL в среднесрочной перспективе).

**Отрицательные / принятые риски (пока откладываем):**
- До миграции проект остаётся на не патчируемой бесплатно линии — каждая новая EOL-CVE требует
  ручного разбора и добавления suppression с обоснованием (процесс уже отработан, но не
  бесконечно масштабируем — см. триггер 1 выше).
- Suppression-файл (`owasp-suppressions.xml`) растёт с каждой находкой — операционные издержки
  на поддержку актуальности обоснований.
- Отложенная миграция технически не становится проще со временем: чем дольше откладываем, тем
  больше расхождение версий и тем крупнее будущий diff (Modulith 1.3→2.x схема, Jakarta-аудит).

**Что это требует от команды дальше:**
- При появлении новой CVE на пиновой линии — сначала попытаться обосновать неприменимость
  (как для уже существующих 5), и только при неудаче — эскалировать как триггер миграции.
- Держать этот ADR актуальным: при срабатывании любого триггера — сменить Status на Accepted
  и завести конкретный эпик в `ROADMAP.md`/`RUN_PLAN.md` с разбивкой на задачи (роль tech-lead).

## Alternatives considered

| Альтернатива | Почему не выбрана (пока) |
|---|---|
| Остаться на 3.5.x + suppression по каждой CVE (статус-кво, выбрано временно) | Рабочий, но не бесконечно масштабируемый компромисс — см. Decision выше |
| Купить Enterprise Support (VMware/Broadcom) вместо миграции | Коммерческая подписка на иностранного вендора — противоречит духу импортозамещения проекта (CLAUDE.md, "без жёсткой привязки к зарубежным проприетарным облакам/вендорам"); не снимает необходимость апгрейда в среднесрочной перспективе, только откладывает его ценой постоянных лицензионных платежей |
| Мигрировать на Boot 4.x прямо сейчас, срочно | Непропорционально объёму текущей задачи (реактивный фикс одной CVE); Spring Modulith 2.x meняет схему `event_publication` — рискованный, объёмный апгрейд не проводится вперемешку с несвязанной работой; требует отдельного спланированного эпика с полным regression-прогоном |
| Форкнуть/пропатчить уязвимые классы локально (vendoring) | Означает поддержку форка Spring Framework/Security силами команды — несоразмерные трудозатраты и риск разойтись с апстримом; ни разу не применялось в проекте для сторонних библиотек |
