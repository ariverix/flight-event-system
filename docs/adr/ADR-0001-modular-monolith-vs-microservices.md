# ADR-0001: Модульный монолит (Spring Modulith) против микросервисов

**Status:** Accepted

**Date:** 2026-06-19

**Authors:** architect

## Context

`flight-event-system` — промышленная отечественная замена модуля **SITA AIRCOM
Sequencer**: движок правил ECA (Event-Condition-Action) для обработки
авиационных сообщений «борт-земля» (ACARS). Заказчик — ФГУП «ЗащитаИнфоТранс»,
эксплуатация в закрытом контуре, не публичный SaaS.

Ключевые свойства предметной области и проекта:

- **Единая транзакционная граница вокруг ECA-движка.** Приём ACARS-сообщения,
  идемпотентная фиксация, продвижение состояния `sequence instance`
  (персистентная стейт-машина), запись в Outbox (`event_publication`) и
  Event Log должны либо закоммититься вместе, либо не закоммититься вовсе.
  Распределённая транзакция через границу сервисов здесь либо невозможна
  (нет 2PC в типовом стеке), либо ведёт к саге с компенсациями — лишняя
  сложность для процесса, который по природе последовательный и
  низкочастотный (десятки-сотни сообщений/сек, не миллионы).
- **Масштаб внедрения.** Один заказчик, один контур развёртывания
  (целевой — Kubernetes/Helm, но без требования автономного скейлинга команд
  разработки). Это не ситуация "200 инженеров, 30 команд, нужна автономность
  релизов" — типичный кейс, оправдывающий микросервисы по Conway's Law.
  Команда разработки — единая, релизит весь продукт целиком.
- **Импортозамещение и эксплуатация в закрытом контуре.** Меньше
  shipped-артефактов, меньше сетевых сегментов между компонентами — проще
  сертификация (ФСТЭК), проще аудит, проще набор средств защиты периметра
  (mTLS/allowlist на единственном внешнем входе — ACARS-эндпоинте), не нужен
  service mesh или брокер сообщений как отдельный аттестуемый компонент.
- **Операционная простота.** Один деплой-юнит, один процесс Flyway-миграций
  (`V1`…`Vxx`, единая БД PostgreSQL), один JVM-процесс для логов/метрик/трейсов
  на старте. Эксплуатирующая организация — не SRE-команда с своим Kubernetes
  Ops, а ограниченный штат на объекте.
- **Домен уже имеет естественные модульные границы.** В системе выделены
  5 модулей (`sequence`, `execution`, `eventprocessor`, `integration`,
  `user`), каждый с собственным публичным API через `package-info.java` /
  `@ApplicationModule`, и есть архитектурный тест
  `ApplicationModules.of(App.class).verify()`, зелёный в CI (см. P0-2).
  То есть структурная модульность — обеспечена независимо от того, в одном
  процессе модули или в разных.

## Decision

Мы строим систему как **модульный монолит на Spring Modulith**, а не как
набор микросервисов.

Конкретно:

1. Один деплой-юнит (один Spring Boot процесс, один артефакт), пять
   модулей с явными границами (`sequence`, `execution`, `eventprocessor`,
   `integration`, `user`), каждый — гексагональный (домен изолирован от
   инфраструктуры через порты/адаптеры).
2. Межмодульное взаимодействие — **только** через публичный API модуля
   (`package-info`/`@ApplicationModule`) или через Spring Modulith Events.
   Прямые обращения к внутренним пакетам другого модуля — архитектурное
   нарушение, отслеживается тестом `ApplicationModules.verify()` в CI.
3. Надёжность доставки между модулями/наружу — через **Transactional
   Outbox** (`event_publication`, см. миграцию V10) в рамках единой
   локальной транзакции БД. Это решает проблему "запись состояния +
   публикация события атомарно" без распределённой транзакции и без
   внешнего брокера сообщений как обязательного компонента инфраструктуры.
4. Единая база данных PostgreSQL 16, единая последовательность Flyway-
   миграций (`V1`…`Vxx`) — одна схема, один источник истины состояния
   ECA-движка (sequence instance state machine, переживающая рестарт).
5. Граница к внешнему миру — гексагональные порты в модуле `integration`
   (ACARS-шлюз вход/выход). Это та точка, где при будущей необходимости
   проще всего вынести adapter в отдельный процесс без переписывания
   домена.

Модульные границы Spring Modulith — это осознанно заложенный **путь к
будущему вычленению сервисов**: если у конкретного модуля появится
самостоятельная причина для отдельного масштабирования или деплоя
(например, `integration` под нагрузкой ACARS трафика на других объектах),
его можно вынести в отдельный процесс с минимальным риском, потому что
публичный API модуля и события уже зафиксированы и проверяются тестом.

## Consequences

**Положительные:**
- Простой деплой: один артефакт, один Helm-чарт, один Flyway-прогон при
  обновлении — меньше точек отказа в продакшне закрытого контура.
- Локальные ACID-транзакции вместо распределённых/саг для критичного пути
  (приём сообщения → переход состояния инстанса → Outbox-запись).
- Меньше инфраструктурных компонентов для аттестации ФСТЭК (нет отдельного
  брокера сообщений, service mesh, нескольких сетевых периметров между
  внутренними сервисами).
- Архитектурные границы проверяются автоматически (`ApplicationModules.verify()`
  в CI), а не только соглашением между разработчиками — деградация в "big
  ball of mud" предотвращается тестом, а не дисциплиной.
- Дешевле локальная разработка и отладка: один процесс, один дебаггер,
  сквозной стектрейс через модули.

**Отрицательные / принятые риски:**
- Нет независимого масштабирования модулей (например, нельзя
  масштабировать только `integration` под пиковую нагрузку ACARS отдельно
  от `sequence`/`execution`). Для текущего масштаба внедрения (один
  заказчик, целевые throughput из RUN_PLAN P2-7) это не является
  ограничением.
- Нет независимого деплоя/релизного цикла модулей — релиз всегда всей
  системы. При единой команде разработки это не создаёт организационных
  издержек.
- Технологическая монокультура (вся система — Java/Spring) — невозможно
  выбрать другой стек под отдельный модуль. Текущие требования (включая
  импортозамещение) не требуют разнородного стека.
- Один процесс — один блок отказа на уровне приложения (но не на уровне
  данных и не на уровне HA, см. P6-1 кластеризация/leader election
  планировщика для будущей multi-replica конфигурации — монолит это не
  исключает: HA достигается через несколько реплик одного и того же
  модульного монолита, не через расщепление на сервисы).

**Что это требует от команды дальше:**
- Держать `ApplicationModules.verify()` зелёным и в CI как обязательный
  гейт (зафиксировано в CLAUDE.md, выполнено в P0-1/P0-2).
- При любом изменении, затрагивающем >1 модуль или публичный контракт
  модуля — проектирование через architect (новый ADR при необходимости),
  не ad hoc.
- Дизайн модуля `integration` (ACARS-шлюз) должен оставаться чистым
  hexagonal adapter, чтобы вычленение в отдельный процесс в будущем (если
  потребуется) не требовало переписывания домена.

## Alternatives considered

| Альтернатива | Почему не выбрана |
|---|---|
| **Микросервисы** (отдельные процессы на модуль, REST/gRPC между ними, брокер сообщений) | Оправданы при множестве независимых команд, разной скорости релизов по доменам, необходимости независимого горизонтального масштабирования конкретных доменов, или когда монолит уже физически не собирается/не тестируется за разумное время. Ничего из этого не выполняется: один заказчик, единая команда, текущий объём кода и тестов (233 теста) собирается и гоняется за минуты. Дополнительная цена — распределённые транзакции/саги для критичного транзакционного пути ECA-движка, лишний сетевой периметр для аттестации ФСТЭК, операционная сложность (брокер, service discovery, distributed tracing как обязательный, а не опциональный компонент). Стоимость превышает выгоду на данном масштабе. |
| **"Big ball of mud" монолит без модульных границ** | Дешевле в моменте, но не даёт инвариантов изоляции домена ECA от инфраструктуры и не оставляет пути к будущему вычленению сервисов без полного рефакторинга. Несовместимо с требованием CLAUDE.md о гексагональной архитектуре и проверяемых границах модулей. |
| **Микросервисы только для `integration` (ACARS-шлюз), остальное — монолит** ("стрэнглер" с самого начала) | Рассматривалось как промежуточный вариант. Отклонено на старте проекта: добавляет сетевую границу и необходимость распределённой идемпотентности уже на этапе P0, когда домен ECA ещё не стабилизирован (типы шагов/критериев допиливаются в P1). Текущая архитектура (hexagonal-порт в `integration`) оставляет этот путь открытым на будущее (см. Decision, п.5) без необходимости платить цену сейчас. |
