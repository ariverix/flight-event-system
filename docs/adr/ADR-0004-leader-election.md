# ADR-0004: Leader election планировщиков на PostgreSQL (lease-таблица), без внешних координаторов

- Статус: Принято
- Дата: 2026-06-27
- Контекст задачи: P6-1 (HA: несколько реплик backend + single-fire планировщика в кластере)

## Контекст

Backend разворачивается в **несколько реплик** (P6-1, `deploy/k8s`, `replicas: 2`). В системе есть
фоновые `@Scheduled`-поллеры: WAIT-таймауты (`WaitTimeoutScheduler`, P1-5) и доставка исходящих
(`OutboundMessageDeliveryScheduler`, P2-3). Если каждая реплика опрашивает БД независимо, возникает
избыточная нагрузка (N реплик × один и тот же опрос).

Важно: **корректность** single-fire (ровно одно срабатывание таймаута/доставки) уже обеспечена
**атомарным DB-claim'ом** в самих планировщиках (`claimExpiredTimeout`/`claimPending` —
условный `UPDATE ... WHERE`, P1-5/P2-3) и работает даже при параллельном опросе всеми репликами.
То есть leader election нужен ради **эффективности** (один опрашивающий), а не как единственный
механизм корректности.

## Решение

**Lease-based leader election на PostgreSQL** (таблица `leader_election`, миграция V36):

- Каждая реплика имеет уникальный `holder_id` (`pid@host` + UUID). Лидерство — строка-аренда с TTL
  (`lease_until`). Захват/продление — единый атомарный `INSERT ... ON CONFLICT (lock_name) DO UPDATE
  ... WHERE leader_election.lease_until < now OR holder_id = me` (`LeaderElectionService`).
- Лидер продлевает аренду каждые 10 c (heartbeat). При его падении аренда протухает, и другая реплика
  атомарно перехватывает её. На shutdown лидер удаляет строку (`@PreDestroy`) — быстрый перехват без
  ожидания протухания.
- `@Scheduled`-тики гейтятся `if (!leaderElection.isLeader()) return;`. DB-claim остаётся
  **defense-in-depth**: кратковременное «раздвоение» лидерства при переходе аренды безопасно.

## Альтернативы

- **`pg_advisory_lock`** (session-level): элегантный авто-failover при разрыве сессии, но lock привязан
  к соединению, что плохо сочетается с пулом Hikari (соединения возвращаются в пул). Lease-таблица
  переоценивается на каждом heartbeat из обычного пулового соединения — устойчивее к разрывам.
- **ShedLock / Quartz-clustering / ZooKeeper / etcd**: внешняя зависимость/координатор. Отвергнуто по
  тем же причинам, что в P1-5 (durable WAIT-таймауты без ShedLock): **импортозамещение** и минимизация
  внешних компонентов — у нас уже есть PostgreSQL как источник durable-состояния.

## Последствия

- (+) HA: несколько реплик, опрашивает одна; автоматический перехват лидерства при падении.
- (+) Без новых внешних зависимостей; пригодно для Реестра российского ПО.
- (+) Корректность не регрессирует: DB-claim независим от leader election.
- (−) Failover не мгновенный при «грязном» падении лидера (до протухания аренды ≈ TTL); приемлемо,
  т.к. опоздавший тик не нарушает корректность (claim), лишь немного сдвигает опрос.
- Настоящая потоковая репликация БД и автоматический primary→replica failover СУБД — вне P6-1
  (инфраструктура БД); здесь — leader election на уровне приложения.
