# ADR-0003: JWT access + refresh-токены (ротация, инвалидизация) и крипто токенов/паролей

**Status:** Accepted

**Date:** 2026-06-23

**Authors:** security-agent

## Context

До P4-2 аутентификация выдавала ОДИН долгоживущий access JWT (24 часа,
`app.jwt.expiration-ms=86400000`), без механизма отзыва: украденный токен
оставался валидным до истечения, «выйти» (logout) на сервере было нельзя
(stateless JWT не отзывается по построению). Пароли уже хэшируются BCrypt
(`SecurityConfig.passwordEncoder`), эндпоинт `/api/v1/auth/login` открыт,
остальное — за JWT (P4-1: RBAC по гранулярным правам).

Требование P4-2: короткоживущий access-токен + долгоживущий refresh-токен с
**ротацией** и **инвалидизацией**; обоснование выбора крипто.

## Decision

### 1. Access (JWT, stateless) + Refresh (opaque, stateful)

- **Access-токен** — JWT HS256, короткий TTL (**15 мин**,
  `app.jwt.expiration-ms=900000`). Остаётся полностью stateless: проверяется
  подписью/сроком в `JwtAuthenticationFilter`, без обращения к БД. Несёт
  `sub`+`role`; роль раскрывается в права в фильтре (P4-1).
- **Refresh-токен** — НЕ JWT, а высокоэнтропийный opaque-токен (256 бит
  `SecureRandom`, base64url). Долгий TTL (**7 дней**,
  `app.jwt.refresh-expiration-ms`). Состояние хранится в БД
  (`refresh_tokens`, V35), что и даёт возможность **отзыва** — то, чего
  принципиально нет у stateless JWT.

Почему refresh не JWT: его ценность именно в отзываемости. JWT отозвать нельзя
без серверного списка (что свело бы на нет stateless-плюс). Opaque-токен с
серверной записью отзывается тривиально (`revoked=true`).

### 2. Ротация + reuse-detection

Каждый `POST /api/v1/auth/refresh` ИНВАЛИДИРУЕТ предъявленный refresh-токен
(`revoked=true`) и выдаёт НОВУЮ пару (access + новый refresh). Если предъявлен
УЖЕ отозванный токен (классический признак кражи цепочки — легитимный клиент уже
ротировал его дальше) — отзываются **ВСЕ** активные токены пользователя, ответ
401. `POST /api/v1/auth/logout` отзывает конкретный refresh-токен.

`/refresh` и `/logout` аутентифицируются САМИМ refresh-токеном (в теле), поэтому
открыты в `SecurityConfig` (как `/login`), доступа по access-JWT не требуют.

### 3. Крипто хранения

- **Пароли** — BCrypt (cost по умолчанию). Пароль низкоэнтропийный → нужен
  намеренно медленный, соль-несущий KDF: BCrypt противостоит брутфорсу.
- **Refresh-токены** — в БД хранится только **SHA-256-хэш** (hex), не сам токен.
  Токен высокоэнтропийный (256 бит) → перебор по хэшу нереален, медленный KDF не
  нужен; SHA-256 даёт быстрый lookup по уникальному индексу `token_hash`. При
  утечке БД токены неюзабельны (хранится хэш). Соль не нужна (нет двух одинаковых
  256-битных токенов, нет «словарного» риска как у паролей).

### 4. Секрет подписи JWT

Секрет берётся из конфигурации (`app.jwt.secret`); вынос из репозитория в
секрет-менеджер и путь к ГОСТ-крипто — отдельная задача P4-3 (здесь не решается).

## Consequences

**Плюсы:** окно компрометации access-токена сокращено с 24 ч до 15 мин; возможны
серверный logout и отзыв; ротация + reuse-detection ограничивают кражу refresh;
access остаётся stateless (без БД на каждый запрос).

**Минусы / долг:** `refresh_tokens` растёт — нужна периодическая очистка
истёкших/отозванных (follow-up, не критично: lookup по индексу). Multi-device —
у пользователя может быть несколько активных refresh-цепочек (это ожидаемо).
ГОСТ-TLS/секрет-менеджмент — P4-3.

## Alternatives considered

- **Только короткий JWT без refresh** — пользователь разлогинивается каждые
  15 мин. Неприемлемо для операторского UI.
- **Refresh как JWT** — отозвать нельзя без серверного денилиста, т.е. всё равно
  нужно состояние; opaque проще и честнее.
- **BCrypt для refresh-токенов** — лишняя стоимость на каждый refresh без выгоды
  (токен высокоэнтропийный); SHA-256 достаточно и быстрее.
