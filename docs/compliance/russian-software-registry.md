## 3. Описание функциональных характеристик

ECA System — программный комплекс обработки авиационных событий по каналу «борт-земля» (ACARS) на основе движка правил типа «Событие-Условие-Действие» (Event-Condition-Action, ECA). Предназначен для автоматизации реакции авиационных наземных служб на сообщения от воздушных судов: мониторинга стадий полёта, автоматической отправки директив экипажу, ведения журнала событий, управления сценариями взаимодействия.

### Основные функциональные возможности:

**Обработка входящих сообщений**
Система принимает авиационные сообщения в форматах ARINC 618, ARINC 620, AFTN и Type B. Производится нормализация, разбор позывных (callsign matching), идентификация борта/рейса и публикация нормализованного события в движок правил.

**Движок правил ECA**
Движок выполняет последовательности шагов (Sequence) трёх типов: ACTION (выполнить действие), EVALUATE IF (мгновенная проверка условия), WAIT FOR (блокирующее ожидание с таймаутом). Каждый шаг оценивает критерии одного из шести типов: получение сообщения (MESSAGE RECEIVED), стадия полёта (FLIGHT STAGE), наличие позиционного отчёта (POSITION), время (TIME), активность условия (CONDITION ACTIVE), а также их комбинации AND/OR. По результату шага выполняется одно из четырёх решений: CONTINUE, GOTO, END, ABORT с опциональным уведомлением.

**Управление последовательностями**
CRUD последовательностей и шагов с версионированием через PostgreSQL и Flyway. Организация последовательностей в папки. Статусы ACTIVE/INACTIVE/DRAFT. Start/Stop Criteria на уровне всей последовательности. Привязка к борту по tail number (регистрационный номер) или через таблицу сопоставления позывных (ICAO-код, даты действия, дни недели, аэропорты).

**Шаблоны сообщений**
CRUD шаблонов для uplink (борт) и ground (наземные службы). Переменные-плейсхолдеры `{{field}}`. Рендеринг с подстановкой custom fields рейса.

**Custom fields**
Автоматическое извлечение данных из входящих сообщений по регулярным выражениям (custom field rules). Переиспользование в исходящих сообщениях.

**Условия и алерты**
Поднятие/закрытие именованных условий (raise/close condition) с уровнями No/Low/Medium/High/Critical. Проверка активности условий в критериях правил.

**Таблица сопоставления позывных (Callsign Matching)**
Конфигурируемая таблица для разрешения позывных рейсов в идентификаторы: ICAO-код авиакомпании, номер рейса, период действия, дни недели, аэропорты вылета/прилёта.

**Реал-тайм мониторинг**
WebSocket-канал (/ws/eca) для трансляции событий выполнения последовательностей в реальном времени. Журнал событий класса Tracking (TrackingEventLog) с партиционированием и retention-политикой.

**Безопасность**
Аутентификация через JWT (access + refresh токены). Ролевая модель (RBAC): роли ADMIN и OPERATOR с детальными правами доступа. Хранение паролей BCrypt. Журнал аудита действий пользователей. Открытый эндпоинт приёма ACARS защищён на сетевом уровне (mTLS/allowlist).

**Наблюдаемость**
Метрики Prometheus (/actuator/prometheus), распределённая трассировка OpenTelemetry (OTLP-экспорт), health-probes (liveness/readiness), структурные логи JSON с correlation_id.

**Высокая доступность**
Механизм leader election на уровне PostgreSQL для координации фоновых задач при горизонтальном масштабировании. Оптимистическая блокировка. Партиционирование нагруженных таблиц.

| Зависимость от зарубежной инфраструктуры | Критичная зависимость от SITA-сервисов и облачной инфраструктуры | Полностью автономная эксплуатация; нет зависимости от зарубежных SaaS |

| Обновления/поддержка | Зависимость от зарубежного вендора | Обновления и поддержка обеспечиваются правообладателем |
| Интеграция с ГОСТ-крипто | Не поддерживается | Путь к ГОСТ TLS задокументирован; архитектура допускает ГОСТ-прокси |
| Совместимость с отечественными ОС | Не заявлена | Работает под OpenJDK 21 (доступен для Astra Linux, РЕД ОС) |
| Функциональный паритет | Эталон (3 типа шагов, 6 типов критериев, 4 решения, start/stop, callsign matching) | 96% паритета реализовано, 4% — в процессе (см. `docs/compliance/parity-matrix.md`) |

**Ключевые преимущества ECA System перед SITA AIRCOM Sequencer** с точки зрения требований Реестра:
1. Полная юрисдикция правообладателя в Российской Федерации.
2. Отсутствие зависимости от зарубежных проприетарных SaaS и облачных сервисов.
3. Весь стек — открытые лицензии (Apache 2.0, MIT, BSD), доступные для верификации регулятором.
4. Возможность развёртывания в изолированном контуре (on-premise) без интернет-соединения.
5. Архитектурная готовность к ГОСТ-криптографии (TLS-терминация на отечественном прокси).
6. Совместимость с отечественными ОС при условии наличия OpenJDK 21 и PostgreSQL 16.

## 6. Совместимость с отечественными операционными системами

ECA System основана на технологическом стеке JVM (Java Virtual Machine) и не имеет платформенно-зависимого кода. Условия совместимости:

| Операционная система | Совместимость | Условия |
|---|---|---|
| Astra Linux Special Edition | Совместима | Требуется установка OpenJDK 21 (доступен в репозиториях или через отдельную поставку), PostgreSQL 16, Docker Engine |
| РЕД ОС | Совместима | Аналогично Astra Linux; RPM-совместимые пакеты OpenJDK 21 и PostgreSQL 16 доступны в официальных репозиториях |
| «Альт» (ALT Linux) | Предположительно совместима | Требует проверки наличия OpenJDK 21 в репозиториях или ручной установки |
| ROSA Enterprise Linux | Предположительно совместима | Аналогично «Альт» |

**Важно:** совместимость с Astra Linux и РЕД ОС не была верифицирована путём тестирования на этих операционных системах на момент выпуска версии 1.0. Верификация требуется до официального подтверждения совместимости в заявлении на включение в Реестр. Тестирование рекомендуется провести на целевом контуре заказчика в рамках приёмочного тестирования (UAT).

## 7. Криптографическая защита и ГОСТ-криптография

**Текущее состояние:**

В версии 1.0 криптографическая защита реализована следующим образом:
- Хранение паролей: алгоритм BCrypt (NIST-рекомендованный, не ГОСТ).
- JWT-подпись: HMAC-SHA256 (не ГОСТ).
- TLS: не настроен на уровне приложения; предполагается терминация на уровне reverse-proxy (nginx/Angie) или Kubernetes Ingress. Приложение слушает HTTP на порту 8080 внутри доверенного периметра.

**Путь к ГОСТ-криптографии (не реализован в версии 1.0):**

Архитектура приложения спроектирована таким образом, что ГОСТ TLS может быть реализован без изменения кода приложения — за счёт развёртывания сертифицированного СКЗИ или ГОСТ-совместимого reverse-proxy перед приложением. Подробная схема задокументирована в `docs/security/gost-tls-path.md`.

Рекомендуемые варианты ГОСТ TLS-терминации:
- Angie (российский форк nginx, ПАО «Вебпрактика», позиция в Реестре российского ПО) со сборкой с ГОСТ-движком.
- КриптоПро NGINX TLS.
- С-Терра Шлюз или аналогичный сертифицированный ФСТЭК/ФСБ шлюз.

**Риск и рекомендация:** применимость обязательных требований к криптографической защите (обязательность сертифицированных СКЗИ, конкретные алгоритмы) определяется категорией обрабатываемой информации и решением регулятора применительно к конкретному контуру заказчика. Уточнить у юриста/compliance ФГУП «ЗащитаИнфоТранс» до прод-развёртывания.
