## Шаг 1. Убедись, что команда собрана
В каталоге `.claude/agents/` должны существовать ровно эти 19 агентов. Если какого-то нет — создай его как Claude Code subagent (Markdown с YAML-фронтматтером `name`/`description`/`tools`/`model: sonnet`), строго по зоне ответственности из `TEAM.md` и `CLAUDE.md`:

Координация: `tech-lead` (декомпозиция, ledger, контроль DoD; без прод-кода), `architect` (ADR, границы Modulith, дизайн подсистем).
Backend: `backend-dev` (общие фичи/API), `sequence-engine-dev` (ядро ECA: шаги/критерии/решения, стейт-машина инстанса, durable-планировщик, resume, конкурентность), `integration-dev` (ACARS/AFTN/Type B, ARINC-парсинг, позывные+matching table, позиции, DLQ/ретраи), `templates-dev` (шаблоны + custom fields), `alerts-dev` (условия/алерты/event handling/уведомления), `db-dev` (схема/Flyway/индексы/партиции/бэкап — все изменения схемы через него).
Качество: `qa-agent` (юниты, покрытие ≥85%), `test-engineer` (интеграционные/контрактные/e2e/нагрузка, resume-тест), `reviewer` (обязательный гейт, только чтение), `bug-fixer` (красное/регрессии/замечания).
Безопасность/инфра/наблюдаемость: `security-agent` (RBAC/JWT+refresh/секреты/TLS-ГОСТ/OWASP/SAST/аудит), `devops-agent` (Docker→k8s/Helm, CI/CD, HA, leader election), `observability-agent` (метрики/трейсы/логи/health/дашборды/SLO).
Frontend: `frontend-architect` (каркас/стор/API-клиент из OpenAPI/WebSocket/i18n), `ui-agent` (экраны, редактор React Flow, UX).
Документы/соответствие: `docs-agent` (OpenAPI, руководство админа RU, ранбуки), `compliance-agent` (импортозамещение/Реестр/ФСТЭК-чеклист/лицензии/матрица паритета).

Tools по умолчанию у dev-агентов: `Read, Write, Edit, Bash, Glob, Grep`. У `reviewer`: `Read, Bash, Glob, Grep` (без правок). У `tech-lead`/`architect`/`compliance-agent`: `Read, Write, Bash, Glob, Grep`.
Старый `feature-agent` ретайрни (удали файл) — его заменили специалисты.

После проверки выведи таблицу: агент → есть/создан → tools.

## Шаг 2. Режим работы (оркестрация)
Дальше ты — диспетчер, а не исполнитель-одиночка:
1. Берёшь ОДНУ задачу (из `RUN_PLAN.md` или от меня).
2. Если задача крупная/неясная — сначала `tech-lead` декомпозирует, кросс-модульная — `architect` даёт ADR.
3. Делегируешь профильному агенту строго по `TEAM.md`. По TDD: тест → реализация.
4. Прогон `qa-agent`/`test-engineer`, затем ОБЯЗАТЕЛЬНО `reviewer`. Красное/замечания → `bug-fixer` → снова `reviewer`.
5. Закрываешь задачу только при выполнении Definition of Done из `CLAUDE.md` (тесты зелёные → coverage ≥85% → reviewer PASS → OpenAPI/доки обновлены → метрики/логи добавлены). Обновляешь `docs/PROGRESS.md`.
6. **STOP** — краткий отчёт (что сделано, доказательства зелёного, что дальше) и ждёшь меня. Я гоняю задачи по одной.

## Жёсткие правила (поверх всего)
- Семантику SITA НЕ упрощать: все 3 типа шагов, 6 типов критериев с AND/OR, решения CONTINUE/GOTO/END/ABORT, start/stop, WAIT-таймауты, «from this point only», авто-закрытие условий — точно по спецификации.
- БД/бэкенд меняем свободно, но ТОЛЬКО через тикет + новую Flyway-миграцию (Vxx) + тесты + ревью. Применённые миграции не трогаем.
- Границы модулей Spring Modulith соблюдаются, `ApplicationModules.verify()` зелёный и в CI.
- Эндпоинт приёма ACARS открыт (внешняя машина без JWT), защита сетевая (mTLS/allowlist) — осознанное решение, документируем. Остальное за JWT/RBAC. Секретов в коде/логах нет.
- Импортозамещение: стек/зависимости пригодны для Реестра российского ПО, путь к ГОСТ TLS.
- Минимум кода под задачу, без абстракций «на будущее».
