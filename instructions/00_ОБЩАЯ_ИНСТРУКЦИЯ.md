# КОНТЕКСТ ПРОЕКТА

## Предметная область (из Главы 1 диплома)

- **ACARS** (Aircraft Communications Addressing and Reporting System) — система цифрового обмена данными между ВС (воздушными судами) и наземными службами. Внедрена в 1978 году, является основным стандартом цифрового обмена данными в авиации.
- **Типы сообщений:** Downlink (борт→земля), Uplink (земля→борт), Ground (земля→земля)
- **Стадии полёта OOOI:** Out (выкатка от гейта), Off (взлёт), On (посадка), In (прибытие на гейт). Это четыре ключевых момента полёта, фиксируемых автоматически. Init — начальная стадия до начала движения.
- **Поток сообщений:** десятки-сотни в минуту (НЕ enterprise-масштаб)
- **Провайдеры:** SITA и ARINC обслуживают тысячи авиакомпаний, обрабатывая миллионы сообщений ежедневно

## Эталонная система — модуль Sequencer (ASP Administrator Guide, раздел 5.13)

Модуль Sequencer из AIRCOM ServerPlatform определяет последовательности и время выполнения действий вне обычного потока обработки сообщений. Последовательность (sequence) — это набор настраиваемых действий (actions) и критериев (criteria), организованных в шаги (steps) для реализации нужных сценариев.

**Ключевой принцип Sequencer:** возможность на основании результата каждого шага определять, что делать дальше — перейти к следующему шагу, перейти к конкретному шагу, завершить или прервать последовательность.

### Три типа шагов:

**ACTION** — единичное действие для ВС, которое даёт результат Successful или Failed:
- Send uplink/ground message — отправить сообщение на борт или наземной службе
- Raise/Close custom condition — поднять/снять пользовательское условие (алерт)
- Wait for a configured amount of time — ждать заданное время

**EVALUATE IF** — мгновенная проверка критерия, результат True или False. Используется как точка ветвления:
- Downlink/Uplink/Ground message + {received} + "template name" — получено ли сообщение определённого шаблона
- Flight stage + {=, >, <, >=, <=, not} + {Init, Out, Off, On, In} — проверка стадии полёта
- Position + {not reported, reported} + {in the last} + {x minutes} — получен ли позиционный отчёт за последние N минут
- Time + {is before, is equal to, is after} + {ETD, ETA, Init, Out, Off, On, In time} +/- {x minutes} — сравнение текущего времени с временной отметкой полёта
- Condition active — активно ли пользовательское условие
- Compound criteria (AND/OR) — составные критерии

**WAIT FOR** — ожидание реализации критерия с таймаутом. Использует те же критерии, что и EVALUATE IF, но не продолжает обработку, пока критерий не станет True или не истечёт таймаут (→ False):
- Таймаут обязателен — настраиваемое время ожидания
- При WAIT FOR в критериях Downlink/Uplink/Ground есть флаг **"From this point only"** — учитывать только сообщения, полученные с момента начала ожидания. Это **критически важная** особенность WAIT FOR, отличающая его от EVALUATE IF.

### Start и Stop критерии:

- **Start criteria** — условие запуска последовательности для конкретного ВС. По сути аналогичны "Wait for", но применяются ко всей последовательности. Пустой start criteria = запуск в начале каждого нового рейса. Start criteria могут быть составными (AND/OR).
- **Stop criteria** — условие остановки последовательности. Оцениваются непрерывно после запуска. При срабатывании — немедленная остановка на любом шаге. Пустой stop criteria = последовательность завершается только через END или ABORT в шаге. Stop criteria также могут быть составными (AND/OR).

### Result Decision Makers (управление потоком):

Каждый шаг завершается одним из двух результатов: Successful (true) или Failed (false). Для каждого результата настраивается решение:
- **CONTINUE** — перейти к следующему шагу по порядку
- **GOTO** — перейти к указанному шагу (по номеру)
- **END** — завершить штатно (нормальное окончание)
- **ABORT** — прервать аварийно

Также для каждого результата можно включить **Notify** — уведомить пользователей об успехе/неуспехе шага.

### Привязка к ВС:

Каждая запущенная последовательность привязана к конкретному ВС и работает с данными этого ВС. Может быть несколько последовательностей для одного ВС одновременно, и одна последовательность может работать независимо для множества ВС.

## Соответствие модели ECA (из раздела 1.3.3 диплома, таблица 1.3):

| ECA-компонент | В Sequencer | Примеры |
|---|---|---|
| **Event** (Событие) | Start criteria, критерии в Wait for | Flight stage = Off, Downlink message received |

## Архитектура (из раздела 1.4 диплома)

- **Архитектурный стиль:** Модульный монолит (Modular Monolith) — 2 Docker-контейнера: приложение + PostgreSQL
- **Паттерн организации кода:** Гексагональная архитектура (Порты и Адаптеры) — бизнес-логика в центре, изолирована от внешних деталей через интерфейсы-порты
- **Паттерн взаимодействия модулей:** Событийно-ориентированный (Spring ApplicationEvents) — модули общаются через доменные события, НЕ через прямые вызовы
- **Паттерн надёжности:** Transactional Outbox через Spring Modulith Event Publication Registry — гарантия доставки событий

> **КРИТИЧЕСКИ ВАЖНО для диплома (Глава 2, раздел 4.3 по ВКР.pdf):** Различай архитектурный стиль (модульный монолит) и архитектурный паттерн (гексагональная архитектура, событийно-ориентированный). Стиль = топология системы. Паттерн = организация кода внутри. Не путай эти понятия в комментариях и документации.

**5 компонентов системы (из раздела 1.4.2 диплома, таблица 1.5):**
1. **Sequence Manager** — CRUD последовательностей, валидация, активация/деактивация
2. **Execution Engine** — движок ECA-правил, управление выполнением экземпляров, переходы между шагами
3. **Event Processor** — приём и классификация входящих сообщений, публикация нормализованных событий
4. **Integration Adapter** — отправка исходящих сообщений, уведомления, взаимодействие с внешними API
5. **Web UI** — пользовательский интерфейс для операторов и администраторов

**4 информационных потока (из раздела 1.4.3 диплома):**
1. Поток входящих событий: REST API → Event Processor → NormalizedEvent (Spring Event) → Execution Engine
2. Поток выполнения действий: Execution Engine → Integration Adapter → HTTP/Log
3. Поток временных событий: Timer Scheduler → TimerExpiredEvent → Execution Engine
4. Поток пользовательских операций: REST API → Sequence Manager → Repository

**Порты системы (из раздела 1.4.4 диплома, таблица 1.6):**

Входные порты (Driving Ports):
- MessageInputPort — приём входящих сообщений (REST-адаптер; в перспективе — AcarsAdapter)
- UserCommandPort — команды пользователей из Web UI (REST-адаптер)
- TimerPort — сигналы от системного таймера (@Scheduled)

Выходные порты (Driven Ports):
- MessageOutputPort — отправка исходящих сообщений (Log-заглушка для MVP; в перспективе — AcarsAdapter/HTTP)
- SequenceRepositoryPort — хранение последовательностей (JPA-адаптер → PostgreSQL)
- ExecutionRepositoryPort — хранение экземпляров выполнения (JPA-адаптер → PostgreSQL)
- NotificationPort — уведомление операторов (Log-заглушка для MVP; в перспективе — WebSocket)

> **Примечание:** В дипломе (таблица 1.6) адаптером для NotificationPort указан WebSocketAdapter. В MVP-реализации используется Log-заглушка. WebSocket-уведомления описываются в разделе «Перспективы развития» при написании Главы 3.

# ЧЕГО НЕ ДЕЛАТЬ

1. **НЕ использовать Kafka / RabbitMQ** — Spring Modulith Events достаточно для модульного монолита
2. **НЕ создавать микросервисы** — модульный монолит (2 Docker-контейнера: app + DB)
3. **НЕ использовать MapStruct** — ручной маппинг DTO ↔ Entity для 5-7 сущностей проще и прозрачнее
4. **НЕ добавлять WebSocket в MVP** — Log-заглушки для NotificationPort, WebSocket упоминается как перспектива в Главе 3
5. **НЕ делать drag-and-drop в React Flow** — только READ-ONLY визуализация
6. **НЕ усложнять безопасность** — простой JWT, 2 роли, без refresh tokens
7. **НЕ использовать Drools** — Easy Rules проще и напрямую отображает модель ECA
8. **НЕ оптимизировать под нагрузку** — это ВКР, не production
9. **НЕ добавлять технологии, не указанные в стеке** — каждая должна быть обоснована в Главе 2
10. **НЕ использовать Spring WebFlux** — MVC проще для понимания и демонстрации
11. **НЕ использовать NONE/UNKNOWN в FlightStage** — только INIT, OUT, OFF, ON, IN
12. **НЕ менять нумерацию UC** — строго UC-01..UC-09 как в таблице 1.4 диплома
13. **НЕ использовать Thread.sleep** — для WAIT_TIME использовать тот же механизм что и для WAIT (waitTimeoutAt + @Scheduled)
14. **НЕ забывать AuditLog** — каждая значимая операция должна записываться
15. **НЕ забывать пагинацию** — все списковые GET-эндпоинты: page, size параметры
16. **НЕ добавлять Summary в FlightStage** — осознанно опущен как нерелевантный для MVP (в ASP Guide есть Summary, но для нашей системы достаточно 5 стадий)
