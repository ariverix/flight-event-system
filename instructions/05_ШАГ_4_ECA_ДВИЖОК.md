# ШАГ 4: ECA-ДВИЖОК (Easy Rules + Execution Engine)

## Что сделать:

Это центральный модуль системы — реализация модели ECA через Easy Rules (см. диплом: раздел 1.3.3, таблица 1.3).

### Три правила Easy Rules (пакет `execution/rules/`):

**ActionStepRule** (@Rule):
- @Condition: `step.getStepType() == ACTION`
- @Action: парсит configJson, определяет ActionType, вызывает соответствующий метод IntegrationService:
  - SEND_UPLINK → integrationService.sendUplink(aircraftId, templateName, params)
  - SEND_GROUND → integrationService.sendGround(recipients, templateName, params)
  - RAISE_CONDITION → integrationService.raiseCondition(aircraftId, conditionName, alertLevel)
  - CLOSE_CONDITION → integrationService.closeCondition(aircraftId, conditionName)
  - WAIT_TIME → записать `waitTimeoutAt = now + durationSeconds`, статус → WAITING. **НЕ используй Thread.sleep!** Реализуй через тот же механизм, что и WAIT-шаги: записать waitStartedAt/waitTimeoutAt и @Scheduled обнаружит таймаут.
- Результат: SUCCESS или FAILURE

**EvaluateStepRule** (@Rule):
- @Condition: `step.getStepType() == EVALUATE`
- @Action: мгновенно проверяет условие из configJson через `CriterionEvaluator`:
  - MESSAGE_RECEIVED → был ли получен указанный тип сообщения для данного ВС
  - FLIGHT_STAGE → текущая стадия полёта ВС соответствует условию (EQUALS, NOT_EQUAL, GREATER, LESS, GREATER_EQUAL, LESS_EQUAL)
  - POSITION_REPORTED → был ли позиционный отчёт за последние N минут. Используются только фактические позиционные отчёты, оценочные позиции игнорируются.
  - TIME_COMPARISON → текущее время соответствует условию относительно временной отметки полёта (IS_BEFORE, IS_EQUAL, IS_AFTER)
  - CONDITION_ACTIVE → активно ли пользовательское условие
  - COMPOUND → AND/OR комбинация других критериев (рекурсивная оценка)
- Результат: SUCCESS (True) или FAILURE (False)

**WaitStepRule** (@Rule):
- @Condition: `step.getStepType() == WAIT`
- @Action: проверяет тот же критерий что и EVALUATE через `CriterionEvaluator`, но:
  - Если True → SUCCESS
  - Если таймаут истёк (waitTimeoutAt <= now) → FAILURE
  - Иначе → null (статус WAITING, продолжаем ждать)
- **КРИТИЧЕСКИ ВАЖНО — fromThisPointOnly:** При проверке MESSAGE_RECEIVED в WAIT-шаге, если `fromThisPointOnly = true`, запрашивать из БД сообщения ТОЛЬКО с `receivedAt > waitStartedAt`. Это ключевое отличие от EVALUATE IF.

### ExecutionService — главная логика (application/):

```java

 * Центральный сервис выполнения последовательностей.

 */
@Service @Transactional
public class ExecutionService {
    /**
     * Основная точка входа при получении любого события.
     * Слушает NormalizedEvent через @ApplicationModuleListener.
     */
    public void processEvent(NormalizedEvent event) {
        checkStartCriteria(event);      // 1. Для всех ACTIVE последовательностей: совпадает ли событие со startCriteria? Если да → запустить новый экземпляр для данного ВС
```

### ExecutionContext:

Record или класс с данными контекста выполнения:
- NormalizedEvent currentEvent (может быть null для таймаутов)
- String aircraftId
- FlightStage currentFlightStage
- LocalDateTime currentTime
- Map<String, Object> additionalData

### Порты и адаптеры:

- `ExecutionManagementUseCase` (port/in/) — для REST: получение списка экземпляров, статуса
- `ExecutionRepositoryPort` (port/out/) — хранение экземпляров
- `ExecutionController` (adapter/in/) — REST API для просмотра статуса выполнения (UC-05)
- `ExecutionJpaAdapter` (adapter/out/) — JPA-реализация

**REST API:**

| Метод | URL | Описание | UC | Пагинация |
|---|---|---|---|---|
| GET | /api/v1/executions | Список экземпляров | UC-05 | page, size, status, aircraftId, sequenceId (фильтры) |
| GET | /api/v1/executions/{id} | Детали экземпляра с историей шагов | UC-05 | — |

**DTO:** `ExecutionInstanceResponse`, `StepExecutionResponse`

**Доменные события:**
- `ExecutionStartedEvent(Long executionId, Long sequenceId, String aircraftId)`
- `ExecutionCompletedEvent(Long executionId, ExecutionStatus finalStatus)`
- `StepTransitionEvent(Long executionId, Integer fromStep, Integer toStep, StepResult result, TransitionAction action)`
- `StepNotificationEvent(Long executionId, Integer stepIndex, StepResult result, String aircraftId, boolean isSuccess)` — для NotificationPort

## Критерий завершения:
Все 3 типа шагов работают. CriterionEvaluator поддерживает все 6 типов критериев + COMPOUND. Unit-тесты покрывают все ветки переходов (CONTINUE, GOTO, END, ABORT) и все типы критериев. @Scheduled таймаут работает.
